## Lucida: Parse, Generate, and Place for Composable Real-to-Sim Scene Modeling

ByteDance Seed + Peking + Zhejiang. [arXiv 2608.30821](https://arxiv.org/abs/2608.30821) · [project page](https://lucida-r2s.github.io/)

Real-to-sim scene modeling: parse posed RGB-D video into an object-centric scene graph with per-instance multi-view "evidence bundles," generate a complete 3D asset per object via amodal image editing + image-to-3D, then place each asset with **GizmoAct** — a VLM policy that treats 9-DoF pose alignment as multi-turn GUI interaction. Headline: scene F-Score 0.924 vs 0.794 for SAM 3D on their new R2S benchmark; ADD-SB@0.05 57.8→83.4% on CA-1M.

**Novelty.** The parse stage (covisibility-weighted keyframe selection, evidence bundles, relation-aware refinement) is careful systems engineering; ablations show it earns real points (mAP 0.597 vs 0.516 with naive keyframing) but each piece exists in prior tracking/scene-graph work. The generate stage is the SceneComplete recipe: amodal completion via image editing, then image-to-3D. The genuinely novel component is GizmoAct: incremental edits expressed in the object's gizmo frame, translation and scale in units of current object size (never absolute pose, never metric scale), a `permute_axis` action resolving coarse rotation by picking one of 24 axis-aligned reorientations from rendered side views, and the policy deciding *stop* from renders alone, where render-and-compare needs an external convergence criterion. Training recipe is also interesting: DART-style error injection in SFT (supervise only recovery actions), then GRPO with quantized two-axis rewards — cuts residual rotation error from 45° to 21° on their hard subset, robust across three initializers without retraining.

**Grains of salt.** The scene-level comparison is partly unfair by construction — SceneGen and SAM 3D get one reference image while Lucida consumes the full multi-view sequence (the paper concedes this). R2S is their own 9-scene benchmark. Results ride on in-house closed components: Seed3D 2.0 image-to-3D, an unnamed base VLM, an unnamed image-editing model.

**Usable.** Nothing literally — no code, no weights, no R2S data, base VLM unnamed. As ideas: GizmoAct's full spec is in §2.3 and is reimplementable, plausibly even zero-shot with a frontier VLM, as a replacement for manual asset placement in Arena scene-building and asset-validation flows. The permute_axis trick and relative, size-normalized action units are portable design rules for any VLM-in-the-loop spatial task. Error-injection SFT plus quantized-level GRPO rewards is a reusable recipe for multi-turn correction policies. The keyframe-selection formula (covisibility × temporal decay) drops into any multi-view capture pipeline.

**Comparable papers.** Closest is [SceneComplete](https://arxiv.org/abs/2410.23643) (MIT, RA-L 2025): same parse–generate–place decomposition from a single RGB-D view of tabletop clutter, registration-based placement where Lucida uses the learned policy. [ACDC](https://arxiv.org/abs/2410.07408) (Stanford, CoRL 2024) is the robot-learning-flavored comparable with the opposite fidelity philosophy: "digital cousins" (similar affordances, retrieved assets) beat faithful twins for policy robustness — reading it against Lucida frames the open question of how much real-to-sim faithfulness robot learning actually needs. Recent contemporary: [physics-aware sim-ready scene estimation](https://arxiv.org/pdf/2602.20150) (2026), which adds the stable-support/no-interpenetration constraints Lucida leaves to optional post-processing.

## LiteReality-Agent

[Project post](https://litereality.github.io/Litereality-agent-site/litereality-agent-post/) · [code (Apache-2.0)](https://github.com/LiteReality/LiteReality-Agent) · extends LiteReality ([arXiv 2507.02861](https://arxiv.org/abs/2507.02861))

iPhone-LiDAR scan (RoomPlan boxes) → per-object reconstruction via TRELLIS or procedural generation → an agent loop that iteratively edits a single `Room.py` scene-as-code file against the capture, with render/measure/material tools and a critic → deterministic QC → GLB/Blend export.

**Novelty: modest but real, in a different place than Lucida's.** Three things stand out. First, scene-as-code grounded in a real capture: prior scene-as-code work (Holodeck/SceneCraft lineage) synthesizes fictional rooms from text; anchoring the code-editing loop to a capture is the new combination, and philosophically it is the GaP move — the deliverable is an inspectable program. Second, articulation: procedural generation gives doors that open and drawers that slide, where Lucida and SceneComplete produce rigid watertight meshes; for manipulation sim that is the difference between set dressing and a usable environment. Third, it ships: code, iOS capture app, Modal-hosted inference — after Lucida released nothing, open-source end-to-end is a practical contribution even if not an intellectual one.

**Grains of salt.** Zero quantitative evaluation (two showcase rooms), no tech report yet, agent-loop internals undocumented. Intellectually an engineering blog post; practically the only thing in this cluster runnable on one of our office scans this week. A GizmoAct-style placement tool would slot naturally into its agent loop.

## VChain vs. World Labs Atlas

[VChain](https://eyeline-labs.github.io/VChain/) ([arXiv 2510.05094](https://arxiv.org/abs/2510.05094), NTU + Eyeline) · [Atlas](https://www.worldlabs.ai/blog/atlas) (World Labs, announced 2026-09-01)

Opposite poles of one question: where does the world knowledge live?

VChain is a tiny inference-time scaffold: GPT-4o reasons out the causally important intermediate states of a prompt, renders them as a sparse set of keyframes ("visual thoughts"), and a per-prompt LoRA nudges a frozen video generator through those waypoints. It is an admission dressed as a method — video generators do not model chains of consequence, so borrow causality from a language model and inject it as sparse supervision. Cheap and model-agnostic; weaknesses are per-sample tuning cost, folk physics from GPT-4o rather than simulation, and no guarantees between keyframes.

Atlas is the maximalist opposite: a from-scratch multimodal autoregressive diffusion transformer unifying text/image/video/3D, pixel-perfect camera control, native 3D scene output from a single image, 1440p up to a minute. Spatial structure baked into the weights rather than injected at inference.

**Read.** They fix different failure axes and are composable, not competitors. Atlas addresses geometric and spatial coherence, but pixel-perfect cameras say nothing about whether *events* follow causally — exactly the axis VChain targets; an Atlas-class model likely still needs something VChain-shaped for multi-step dynamics. Conversely VChain inherits every geometric weakness of the generator under it. Same dichotomy as the GaP thesis — harness intelligence at inference time versus amortize it into weights — playing out in world models. Genre difference matters: VChain is a reproducible paper with an award; Atlas is a product announcement with demos, no paper, no weights. One is a method, the other currently a claim. Robotics angle: Atlas-class 3D-native output is a potential future competitor to Lucida-style real-to-sim pipelines; VChain is evidence for the skeptical position on video models as robot world models — the causal reasoning had to be imported from outside.

## FACT: Failure-Aware Causal Training for World-Action Models

UCSD (Xiaolong Wang's lab). [arXiv 2608.10232](https://arxiv.org/abs/2608.10232) · [project page](https://fact-wam.github.io/) · [code, Apache-2.0](https://github.com/Bariona/FACT) · [sim checkpoint](https://huggingface.co/Bariona/fact-wam)

A single causal diffusion transformer (initialized from Wan2.2-TI2V-5B) jointly denoises robot action chunks, a task-progress value, and future video in one sequence. The ordering is "act, then imagine": world-side predictions (value + future video) attend only to the clean *executed* action, never the noisy action slot being denoised. That layout lets failure rollouts become training data — mask the imitation loss, still supervise the observed failed future and a lowered value. Results: +6.4 dB PSNR predicting futures of failing actions (quantified success-bias reduction), a value head action-sensitive enough for best-of-N ranking, 87.5% on RoboTwin at ~3× the speed of Motus, and real-world bimanual 82→89% from failure co-training (92% with scoring, seen tasks).

**Novelty.** Joint video+action(+value) diffusion: repackaged (UVA, UWM, Motus, τ₀-WM). Failure rollouts supervising world/value but not imitation: incremental — [τ₀-WM](https://arxiv.org/abs/2606.01027) (concurrent, ~2.5 months earlier, 27,000-hour scale) already trains on failures with modality masks and a progress head, [World-VLA-Loop](https://arxiv.org/abs/2602.06508) already diagnosed success-hallucination and fixed it with rollout training, and Dreamer-line MBRL has always trained dynamics and value on all experience. Best-of-N with a learned verifier: repackaged (RoboMonkey). The single genuinely novel element is the causal teacher-forcing token layout that makes failure data insertable without contaminating the policy loss or leaking future into action. FACT is the cleanest isolated *study* of the failure-data recipe — ablations, a non-saturating failure-scaling curve — not its inventor.

**Grains of salt.** Doesn't beat Motus on RoboTwin success (87.5 vs 87.8; the win is speed, and only vs video-generating WAMs, not plain VLAs). On real-world unseen tasks FACT (82%) sits below π0.5 (85%); the headline progression is a seen-task self-ablation where failure data is extra data baselines don't receive. Own platform, 20 trials/cell, self-run baselines. Real-robot weights and datasets unreleased.

**Usable.** One of the very few fully open WAM training stacks (code + sim checkpoint + closed-loop RoboTwin eval). Three portable recipes: imitation-mask failure co-training (~30 failures/task sufficed on hardware); clean-action conditioning against future→action leakage for any DreamZero-style joint predictor; failure-trained value head as a bolt-on best-of-N verifier — success-only value heads are action-insensitive.

## Hydra-0: Action Flow as the Interface Between Physics and Video Models

NVIDIA + Brown/Columbia/Harvard. [arXiv 2608.18077](https://arxiv.org/abs/2608.18077) · [project page](https://nvidia-isaac.github.io/video_to_data/hydra-0/)

Naming trap first: despite living under the `video_to_data` Pages site, Hydra-0 is not the V2D/CHORD pipeline (a separate, [code-released project](https://github.com/nvidia-isaac/video_to_data) that extracts poses/meshes from human video into Isaac Lab RL). Hydra-0 is an **action-conditioned video world model** — the generative direction is action→video, a neural simulator. "Video to data" describes only its training-time trick: a point tracker plus grounded masks extract "action flow" (pixel-plane trajectories of the visible embodiment, split from object tracks) out of 2,202 hours of unlabeled interaction video across four embodiment classes (human hands, UMI grippers, Franka, bimanual YAM), so one model trains with no shared action space. At deployment it runs as a hybrid simulator: Isaac Lab executes the robot command exactly, the commanded link transforms project through a calibrated camera into image-plane flow, and the video model predicts everything physics can't model — cloth, deformables, contact, lighting. Same model does open-loop policy evaluation (Pearson r = 0.96 against NVIDIA's RoboLab sim over 300 episodes) and, run in reverse on desired *object* flow, generates robot motion that a supervised readout converts to 14-DoF commands.

**Versus video generation models — the asked question.** It *is* one, but with an opposite role to the data-engine class: DreamGen/GR00T-Dreams run prompt→video→pseudo-actions to mint VLA training data (video model as data factory); Hydra-0 consumes actions and predicts consequences (video model as environment). Cosmos is literally one of its backbones — the paper's central experiment swaps Cosmos's native 6D action conditioning for flow on the identical backbone and wins across every metric (gripper EPE 34.28 → 13.80 px), making this a conditioning-interface paper *about* models like Cosmos rather than a rival family. DreamZero is the closest relative of the inverse mode, but is a real-time closed-loop policy where Hydra-0's readout is open-loop, one task, and needs task-specific real rollouts. The contrast with Genie-class latent actions: both dodge native action labels, but Genie's latent actions aren't physically addressable, while action flow is computable analytically from URDF + calibration — a bridge from a physics engine into the conditioning space that latent-action models don't have.

**Novelty.** Track-conditioned video generation is repackaged (ATI, Wan-Move, Motion Prompting — ATI is their own zero-shot baseline). Flow as embodiment-agnostic action abstraction is incremental over ATM/Track2Act/Im2Flow2Act, and [JOPAT](https://arxiv.org/abs/2605.23856) put 2D tracks inside a world-action model three months earlier as a prediction target. World-model-as-policy-evaluator is incremental over [Ctrl-World](https://arxiv.org/abs/2510.10125), which is closed-loop where Hydra-0 only replays. The genuinely novel element is the **hybrid physics/learned simulator with kinematically projected action flow as the seam**: the same interface a tracker recovers from unlabeled video at training time is computed exactly from the robot model at deployment (with a concrete 1.2 cm / 3×3 depth-buffer visibility test). No prior instance found, and it's what makes train-on-anything / deploy-calibrated cohere. Second: the controlled same-backbone flow-vs-native comparison is a clean, transferable finding.

**Grains of salt.** The 90.4% headline is against their weakest baseline; zero-shot ATI (4.62 px) already sits near Hydra-0 (3.29 px) on robot motion, and there's no fine-tuned track-conditioned baseline on the same corpus — flow-vs-native is controlled, flow-vs-flow is confounded by training data. The r = 0.96 evaluator result is measured against NVIDIA's own simulator with a human rater on replayed achieved trajectories — sim-consistency, not real-world predictivity, and not prospective evaluation of unexecuted commands (the page concedes this). Held-out sets are splits of the training corpus's own datasets. And nothing is released: paper and videos only, code and weights "coming soon," same-org loop throughout (NVIDIA model, NVIDIA benchmark, mostly NVIDIA policies).

**Usable.** Downloadable today: nothing from Hydra-0 itself; [ATI weights](https://huggingface.co/bytedance-research/ATI) give zero-shot track-conditioned generation and [RoboLab](https://github.com/NVlabs/RoboLab) is public. The cheap experiment worth stealing: on any action-conditioned world model, swap native action conditioning for tracker-derived embodiment flow — the same-backbone ablation suggests large gains and needs no action labels. The recipes are stated with unusual precision (conditioning-mode sampling 0.40/0.40/0.15/0.05; 480p/16 fps/81-frame windows with a 50-px track-length floor; the visibility test) and are directly reimplementable. The hybrid-simulator pattern — physics engine owns the calibrated robot, video model owns the unmodeled world, projected flow as the hand-off — is the idea most worth reimplementing for policy evaluation on deformables: it skips asset and material modeling entirely, at the cost of open-loop-only fidelity for now.

## Cross-comparison: Hydra-0 vs Cosmos vs DreamZero vs Atlas

One line each: Cosmos is the substrate, DreamZero is a policy, Hydra-0 is a simulator, Atlas is a world renderer.

| | Cosmos (Predict 2.5) | DreamZero | Hydra-0 | Atlas |
|---|---|---|---|---|
| What it is | World foundation model platform: pretrained video predictors you post-train | 14B world-action model: predicts video + actions jointly | Action-conditioned video world model + physics hybrid | From-scratch multimodal AR-diffusion world model |
| Role | Substrate for physical AI | The robot's brain (zero-shot policy) | The robot's environment (sim + policy evaluator) | Spatial/world generation (camera-controlled video + native 3D) |
| Action interface | Native actions (post-trained variants) or text/image | Native actions, generated jointly with video | Action flow: pixel-plane tracks, computable from URDF + calibration | Camera trajectories, not robot actions |
| Loop | Depends on post-training | Closed-loop, real-time-ish | Open-loop (replay/rollout) | Offline generation |
| 3D | No (2D video) | No (2D video) | Via Isaac Lab on the physics side | Yes, native |
| Released | Most open: [weights + code + tokenizers](https://github.com/nvidia-cosmos/cosmos-predict2.5), [action-conditioned variant](https://huggingface.co/nvidia/Cosmos-Predict2-2B-Sample-Action-Conditioned) | [Repo](https://github.com/dreamzero0/dreamzero), [paper 2602.15922](https://arxiv.org/abs/2602.15922) | Nothing (paper + videos) | Nothing (product demos) |

The genealogy places the NVIDIA trio. Cosmos ([2501.03575](https://arxiv.org/abs/2501.03575)) is deliberately unfinished: a pretrained video-prediction base plus tooling to post-train it, which is why it appears inside both of the others. DreamZero's thesis is what you get when a big video backbone is finetuned to emit actions alongside video: the video model *is* the policy (2x generalization over SOTA VLAs, 30-minute embodiment adaptation), inheriting the failure mode of confident, physically wrong futures that FACT's failure-training targets. Hydra-0 bets the opposite role: keep the policy separate, use the video model as the *world*, split labor with a physics engine (Isaac Lab executes the rigid robot exactly; the video model handles cloth and contact; projected action flow is the seam) — and it uses Cosmos 2.5 as a backbone while showing its native action conditioning loses to flow on the same backbone. Policy-in-the-model versus policy-outside-the-model is the real axis between DreamZero and Hydra-0, and they compose: one could evaluate DreamZero inside Hydra-0.

Atlas is the outlier on every axis: different company, different target (spatial intelligence/content, not manipulation), from-scratch unified text/image/video/3D instead of post-trained video, and its "actions" are camera moves — steering the observer, not an embodiment. It is the only 3D-native model of the four, which is exactly what the NVIDIA three lack (Hydra-0 borrows 3D from the physics engine instead of learning it). No action conditioning, no paper, no weights; pixel-perfect camera control says nothing about causal event dynamics (the VChain point). If Atlas grows an action interface it becomes a Cosmos competitor; today it is closer to a generative Lucida than to a robot world model.

Practical ranking today: Cosmos is the only one you can post-train right now; DreamZero is the one to benchmark as a policy; Hydra-0's hybrid pattern is the one to reimplement for deformable policy evaluation; Atlas is the one to watch for real-to-sim scene generation, not control.

## ENPIRE vs ASPIRE: NVIDIA GEAR splits the agents-as-robotics-engineers problem

[ENPIRE, arXiv 2606.19980](https://arxiv.org/abs/2606.19980) (June 19, 2026) · [ASPIRE, arXiv 2607.00272](https://arxiv.org/abs/2607.00272) (June 30, 2026; 14 authors incl. Ken Goldberg) · [ASPIRE code, Apache-2.0](https://github.com/NVlabs/ASPIRE)

Eleven days apart, same lab family, complementary halves. ENPIRE is physical autoresearch: the policy is a learned model (offline RL, VLA+GOFE mixes per its own cut margin notes), and coding agents do everything around it — phase one builds an "agent-operable" environment from human feedback (reward code, automated reset, safety boundaries, frozen into immutable APIs), phase two autonomously runs the research loop on an 8-station bimanual YAM fleet: propose training recipes, launch runs, evolutionarily select hypotheses by success rate, with MTU/MRU as efficiency metrics. Pin insertion converges to 100% faster than a human-in-the-loop baseline. Everything on real hardware; that is the thesis.

ASPIRE (Agentic Skill Programming through Iterative Robot Exploration) is continual code-as-policy: the policy *is* the code the agent writes and refines, with validated fixes distilled into a growing transferable skill library, driven by a closed-loop execution engine with multimodal traces and evolutionary search over task sequences. Iteration happens in simulation — LIBERO-Pro (+77% under perturbation; 31% vs 4% on LIBERO-Pro Long), Robosuite bimanual handover (+72%), BEHAVIOR-1K (+32%) — with sim-to-real as preliminary evidence.

The axis: both belong to the code-as-policy family; what separates them is the rehearse/revise loop. ASPIRE is code-as-policy with iterative rehearsal as the engine — the agent revises the policy artifact itself, execution by execution, against cheap simulated rollouts, and compounds validated revisions into the skill library. That is GaP's self-learning move made continual. ENPIRE runs the same loop against real hardware, and the price of a physical rollout forces two changes: the revision target climbs a level of abstraction (training recipes, reward code, and environment infrastructure rather than per-rollout edits to the acting code — nobody can afford to debug a Python policy at minutes per physical trial), and the policy being improved becomes mostly learned (offline RL, VLA+GOFE mixes) rather than written. Same loop, different medium; the medium's cost determines what the agent can afford to revise. ENPIRE's weak point follows from the same economics: it must synthesize its own reward code on hardware, which its own commented-out draft flags ("Not actually verifiable" — Tonghe's note on the Verifiable Reward paragraph). Both use evolutionary selection over different populations: ASPIRE over tasks/skills, ENPIRE over training-recipe hypotheses across a fleet.

The GaP thread runs through both. ASPIRE is GaP's closest sibling (Goldberg on both; agentic code-as-policy + skill library), trading the typed graph and one-shot rehearsal for continual skill compounding and auto-curriculum. ENPIRE is the missing piece the GaP post ends on: the on-robot correction stage, real-world checkpoints, rig error inside the loop. GaP/ASPIRE own the sim side; ENPIRE owns the real side; nobody has shipped both halves in one system yet.

Release asymmetry: ASPIRE is runnable today (Apache-2.0 sim framework, agent runbooks, coding-agent agnostic — their preferred setup is Claude Code, with Codex used for the real-robot runs); ENPIRE shipped paper and videos only. To run one this week: ASPIRE. As the blueprint for fleet automation: ENPIRE.

## Scene-as-code vs policy-as-code vs graph-as-policy: one architecture, three artifacts

The week's papers sort into three "agent writes an artifact" paradigms, distinguished by what the artifact denotes. Scene-as-code (LiteReality-Agent's `Room.py`; the Holodeck/SceneCraft lineage; procedural generators like Articraft) encodes a *state*: run it once and a world exists. Policy-as-code (CaP, CaP-X, ASPIRE) encodes a *behavior*: run it repeatedly and a robot acts. Graph-as-policy (GaP) encodes a *workflow*: a typed composition of skills that an interpreter walks, sitting between the other two — more structured than free-form code, more behavioral than a scene.

**They converge on the same five-piece stack.** (1) An authoring agent, usually multi-agent, that writes the artifact. (2) A typed substrate: GaP's graph schema with a shared type system, ASPIRE's skill signatures, `Room.py`'s scene API. (3) An LLM-free executor: GaP's interpreter, the Python runtime, Blender. (4) A verification loop that grades executions and feeds failures back to the agent: GaP's N-scene rehearsal with per-node validation rates, ASPIRE's fix loop over multimodal traces, LiteReality's render-and-compare critic, CaP-X's visual differencing, ENPIRE's real-world verification APIs. (5) A library that the artifact draws from: MORSL's 85 entries (fixed, human-authored), ASPIRE's skill library (growing), LiteReality's materials and procedural generators. The paradigms differ mainly in which piece is load-bearing: scene-as-code lives or dies by its critic (cheap renders, single-sample), graph-as-policy by its rehearsal statistics (expensive rollouts, distributional), policy-as-code by its library compounding.

**Borrowing across the three is straightforward.** GaP's statistical verification (30 sampled scenes, per-node failure rates) would fix scene-as-code's weakest link — LiteReality's critic judges one render, where N viewpoint/lighting re-renders with per-object scores would catch what single samples miss. ASPIRE's compounding library would fix GaP's: MORSL is frozen and GaP's "invented skills" are per-task disposables; distilling validated graph fragments back into the catalog is exactly ASPIRE's move. LiteReality's articulation-aware procedural generation would upgrade GaP's rehearsal scenes, whose belief space samples poses but not scene structure. GizmoAct is a drop-in placement skill for any of them. And ENPIRE's immutable-API discipline — freeze verified interfaces, iterate only above them — is the boundary hygiene all three need but none states.

**The second set of borrowings is from domains that have run "artifact-as-code plus verification" for decades.**

*Infrastructure-as-code (Terraform, Kubernetes).* The plan/apply separation: diff the declarative artifact against live state and show the diff before executing. A scene file diffed against current perception before a rehearsal run; a policy-graph edit diffed as "nodes changed, checkpoints affected." Deeper: the reconciler pattern — Kubernetes controllers continuously reconcile desired state against actual state. A scene-as-code file treated as desired state with a perception-driven reconciler is a genuinely new framing for workcell monitoring: drift detection for the physical world.

*CI and software engineering.* Golden regression suites: every failure the agent fixes should become a permanent scene in the rehearsal set, so no later graph edit can silently regress it. GaP re-samples its belief space each iteration and keeps no regression corpus; software learned this lesson in the 1990s. Plus bisection over artifact edits when a regression does appear — the same machinery as our director's-cut bisector, pointed at policy history.

*Hardware verification (EDA).* The closest structural match, because chips are also "compile once, execute forever, failure is expensive." Coverage metrics: verification engineers measure which branches a testbench exercised and refuse sign-off below a threshold. GaP samples scenes blindly and reports success rates; nobody asks "did rehearsal ever exercise the failure-recovery edge of this graph?" Branch-coverage-driven scene sampling would target rehearsal at unexercised graph paths. And temporal assertions (SVA-style): "gripper never opens while transporting," checked continuously during rollout — GaP's checkpoints are postcondition-only and, per the GaP post, don't run on real hardware at all.

*Database query optimization.* SQL separates declarative intent from execution plan, and the optimizer picks operators using cost statistics. GaP's LLM currently selects skills by judgment; it already collects per-node success rates and cycle times — a cost-based optimizer over MORSL (with EXPLAIN output: "chose grasp_moe because grasp_curobo_obb fails 40% on off-center handles") would make skill selection statistical rather than vibes, and auditable. Adaptive re-optimization mid-execution maps to runtime skill swapping on repeated node failure.

*Game development.* Prefab variants: scenes inheriting from a base with overrides, so one validated workcell template spawns many concrete cells — the reuse story none of the robotics scene systems have. Deterministic replay for debugging. And Storybook-style isolated harnesses: every library skill gets a standalone scene that exercises just it, with golden-render snapshot tests — unit tests for MORSL entries, which today are validated only inside whole-task rehearsals.

The common thread: robotics is rediscovering, one paper at a time, the verification infrastructure that software, hardware, and infrastructure engineering built once failure got expensive. The artifacts are new — graphs, scenes, skills — but plan/apply, regression suites, coverage-driven testing, cost-based optimization, and reconciliation loops transfer almost unchanged, and mostly haven't been tried.
