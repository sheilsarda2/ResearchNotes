## Risks

1. **ROS build cost and memory.** A full colcon build of rosbag2 with tests is heavy; 8 GB with four g++ jobs on gmock/rclcpp TUs may OOM (fallback: `WS_MAKE_JOBS=1`, or `WS_COLCON_WORKERS=1`). Build timeouts are 2 h; the agent's edit-build-test loop is 30-45 min per full cycle (incremental single-package rebuilds are minutes), which is the horizon argument but also the main usability cost.
2. **Rolling drift.** `ros:rolling` and the `ros2-testing` apt repo are moving targets; the digest pin freezes the image but `rosdep install` at build time pulls current rolling debs. If rclcpp/rmw move ABI under rosbag2 0.34.0 before the build phase, the build breaks; mitigation is to snapshot the needed debs into `environment/` in the build phase (or pin to `ros:kilted` and re-target the PR, not backported).
3. **RMW discovery in `network_mode = none`.** `test_play`, `test_serialization_converter` and the CLI check need Fast DDS to discover on loopback/SHM inside a container without a network. `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST` and unique `ROS_DOMAIN_ID`s are set; if discovery fails, add `ROS_STATIC_PEERS=127.0.0.1` or a Fast DDS XML profile with UDPv4 unicast only, or move the play checks to in-process `rosbag2_transport::Player` in the C++ harness.
4. `mcap_vendor` downloads mcap v2.1.3 via FetchContent at image build (network OK there); the verifier never rebuilds it.
5. Static gtest counts may be off by parametrization details (see above).
6. Scope limits: only `src/`/`include/` transfer, so an agent cannot add translation units; stated in the instruction.
7. Anti-cheat greps reject `system(`, `popen(`, `getenv(`, `gtest` etc.; none appear in the pristine six packages, but a legitimate `getenv` use would be rejected. Acceptable for this task; documented.
