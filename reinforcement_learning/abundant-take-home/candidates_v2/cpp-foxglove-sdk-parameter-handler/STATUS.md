## Chosen feature

foxglove/foxglove-sdk PR #1258 "cpp: Introduce ParameterHandler for asynchronous parameter operations" (gasmith, merged 2026-05-23, squash commit `a9e4bb7a`). Base = first parent `b2fb3fab2954d34fba6408fff1b4b7a7d58e6bab` (2026-05-22).

Scope decision: **C++ SDK plus C ABI glue over the fixed Rust core**, the PR's own boundary. The Rust `ParameterHandler` trait and both responders already exist at the base commit (`rust/foxglove/src/remote_common/parameters.rs`), so the C ABI is pure FFI glue and the agent must design it (opaque responders with `into_raw`/`from_raw` ownership transfer, `#[repr(C)]` handler struct with Send/Sync justification, option fields appended last, cbindgen rename tables, header regeneration) and then write the C++ wrapper for both the WebSocket server and the remote-access gateway. Remote access is built (`FOXGLOVE_REMOTE_ACCESS=ON`, the upstream default for `make -C cpp build`) so the gateway wiring is compile-verified; only the WebSocket path is exercised at runtime.

Gold patch (non-test): 17 files, +1294/-125. Hand-written: ~379 lines Rust FFI, ~510 lines C++ (+26 deleted), 6 lines cbindgen config; generated header +202; example rewrite +180/-99; ROS bridge +26 (pragma suppression, not built here). Hidden tests: 5 new Catch2 cases (+459 lines) in `cpp/foxglove/tests/test_websocket.cpp`.

## Risks

1. **Image build time / offline completeness.** The remote-access stack is heavy and has two out-of-band network steps (crates and libwebrtc) that are pre-seeded but unverified here; a missed `rerun-if-env-changed` or an aws-lc-sys pregenerated-bindings gap on the validation host arch would surface at build validation. Fallback: `FOXGLOVE_REMOTE_ACCESS=OFF` and drop the gateway from scope (patch hunks are separable).
2. **Reference-server compile assumptions.** `GetParametersResponder` moved into `std::thread::spawn` must be `Send`; `WebSocketServer::start_blocking` / `stop().wait_blocking()` signatures were read from the base tree but not compiled. Fix-ups belong in the verifier image, not the task.
3. **Transcript nondeterminism.** Any core-emitted message that varies per run (an `advertise` with zero channels, ordering of serverInfo extras) would show up on both sides identically, but the reference sanity check pins exact contents of a few messages; if the core emits something unexpected, sanity fails loudly and the scenario script must be adjusted.
4. **Instruction strictness.** The C API and C++ signatures are specified verbatim (they are the hidden tests' and drivers' compile contract); a model that renames a type fails to compile the hidden tests. This is intended (upstream API is the spec) but makes the reward binary on naming.

## Validation log (2026-09-13, arm64 Docker Desktop, 8 GB VM, 4 cpus per container)

### Run 1 — `cpp-foxglove-sdk-parameter-handler-oracle-20260913T124336Z` (and the paired nop): build failure

Both trials died in the agent image build (Dockerfile step `make -C cpp build PARALLEL_JOBS=4`, ~90 s in):

```
error[E0658]: `#[target_feature(..)]` can only be applied to `unsafe` functions
error[E0133]: call to unsafe function `std::arch::aarch64::vaddq_s16` is unsafe and requires unsafe function or block
   --> /usr/local/cargo/registry/src/index.crates.io-1949cf8c6b5b557f/zune-jpeg-0.5.9/src/upsampler/neon.rs:126:45
error: could not compile `zune-jpeg` (lib) due to 21 previous errors
```

Cause: the image installed Rust 1.85.0 (the workspace `rust-version`). The locked `zune-jpeg 0.5.9`
(`image 0.25.9` <- `img2yuv` <- `remote-access`) declares `rust-version = 1.75` but its aarch64-only
NEON upsampler uses safe `#[target_feature]` functions (stable since 1.86.0) and calls NEON intrinsics
from them without `unsafe` (allowed since 1.87.0; 0.5.8 had honestly declared MSRV 1.87.0). The module is
not compiled on x86_64, so the MSRV is only wrong on aarch64. Upstream never hit this: the MSRV job
(`cargo +1.85.0 build -p foxglove`) runs on x86_64 with default features (no `image`), and the
`aarch64-unknown-linux-gnu` remote-access job builds with `stable`.

Remedies considered:
- `cargo update -p zune-jpeg --precise <older 0.5.x>` inside the image: no older 0.5.x compiles on 1.85
  aarch64 either (0.5.5-0.5.7 carry the same NEON code; 0.5.8 needs 1.87), it changes `Cargo.lock` (the
  verifier restores the pristine lockfile, so it would have to be patched in both images and would show
  up as a dirty tree for the agent), and `--locked`/`--frozen` are not the issue (the Makefile/CMake pass
  neither).
- Disabling `img2yuv`/`image` through the environment: impossible, cargo features are not env-controlled
  and `remote-access` hard-enables `img2yuv`.
- Newer Rust on aarch64 only (chosen): `ARG RUST_VERSION_AARCH64=1.87.0`, selected by `uname -m` in the
  rustup step of both Dockerfiles. x86_64 keeps 1.85.0 exactly, so the amd64 image content is unchanged.
  Probes on this host (`rust:<ver>-slim-bookworm`, aarch64, locked registry from `cargo fetch --locked`,
  `cargo check -p foxglove --no-default-features --features img2yuv --offline`): 1.85.0 fails (E0658+E0133),
  1.86.0 fails (E0133 only), 1.87.0 passes for zune-jpeg 0.5.9, moxcms 0.7.11, image 0.25.9, yuv 0.8.9.
  `cargo check -p parity_refserver --offline` (the verifier's Rust reference server as a workspace member
  of the pristine tree) passes on 1.86.0 and 1.87.0, so the refserver's API assumptions hold.

### Run 2 — `cpp-foxglove-sdk-parameter-handler-oracle-20260913T125757Z`: build failure (nop stopped by hand)

zune-jpeg now compiles; the warm build died ~95 s in, in the C crate's build script:

```
error: failed to run custom build command for `foxglove_c v0.24.0 (/workspace/repo/c)`
  Unable to generate bindings: CargoMetadata("/workspace/repo/c/Cargo.toml", ... stderr: "error: failed to download `addr2line v0.24.2`
  Caused by: attempting to make an HTTP request, but --offline was specified
```

Cause: `c/build.rs` runs cbindgen 0.29, which shells out to `cargo metadata --all-features` without
`--filter-platform` (the crate's `cbindgen.toml` has no `[parse] only_target_dependencies`), so cargo must
read the manifest of every package in `Cargo.lock`, including platform-foreign ones. The image had run
`cargo fetch --locked --target <host>` (468 crates); `cargo metadata` needs all 587. Probe (rust 1.87.0
container, same registry): offline metadata fails before and succeeds after a target-less
`cargo fetch --locked` (994 MB registry, 612 packages in the metadata). Fix: `RUN cargo fetch --locked`
(all platforms) in both Dockerfiles. Same effect on amd64 (a superset of the crates it fetched before).
Follow-up probe: `cargo check -p foxglove_c --offline` on 1.87.0 passes (cbindgen and aws-lc-sys build
scripts run) and the regenerated `foxglove-c.h` is byte-identical to the committed one, so
`header_in_sync` is toolchain-agnostic.

### Run 3 — `cpp-foxglove-sdk-parameter-handler-oracle-20260913T130429Z`: build failure (nop stopped by hand)

Past cbindgen; the `foxglove` crate itself failed at ~100 s, and this one is not arch-specific:

```
error[E0658]: `let` expressions in this position are unstable
   --> rust/foxglove/src/remote_access/connection.rs:240:16
   --> rust/foxglove/src/remote_access/session.rs:2119:20
error: could not compile `foxglove` (lib) due to 2 previous errors
```

Cause: let chains (stable since Rust 1.88.0, edition 2024) inside the `remote-access` module. Upstream's
MSRV job (`cargo +1.85.0 build -p foxglove`, default features) never compiles that module; every
remote-access CI job (ubuntu-22.04, ubuntu-22.04-arm, macOS, Windows) builds with `stable`. So the
1.85.0 pin was wrong for this task's `FOXGLOVE_REMOTE_ACCESS=ON` build on x86_64 as well, and the
"keep amd64 byte-identical" arch-conditional toolchain from run 2 was solving the wrong problem.

Decision: pin Rust **1.95.0** on every architecture (`ARG RUST_VERSION=1.95.0`), the stable release
current at the base commit (1.95.0 shipped 2026-04-16, 1.96.0 on 2026-05-28, base is 2026-05-22), i.e.
what upstream CI built this exact tree with. The arch-conditional `RUST_VERSION_AARCH64` was removed
again. Probe on 1.95.0 (aarch64): `cargo fetch --locked` accepts `Cargo.lock` unchanged;
`cargo check -p foxglove_c --offline` passes with a byte-identical regenerated header;
`cargo check -p foxglove --no-default-features --features img2yuv,websocket-tls,sysinfo,lz4,zstd,aws-lc-rs`
passes; `cargo check -p parity_refserver` passes. Not probed outside Harbor: the livekit/webrtc-sys
compile (needs the libwebrtc bundle), which the image build exercises.

Not a relaxation of any check: `instruction.md` names no Rust version; the verifier is unchanged.
Additional probe before run 4 (rust:1.95.0-slim-bookworm, aarch64, g++ 12, libglib2.0-dev/libva-dev,
`LK_CUSTOM_WEBRTC` pointing at the same webrtc-51ef663 linux-arm64 bundle the Dockerfile pre-extracts,
`CXXFLAGS=-fpermissive`): `cargo build -p foxglove --features remote-access --offline` finishes in 88 s
(webrtc-sys 0.3.32, livekit 0.7.42, libwebrtc 0.3.34, zune-jpeg 0.5.9, yuv 0.8.9 all compile), and
`cargo check -p foxglove_c --features remote-access --offline` (the feature set corrosion builds; compiles
`c/src/gateway.rs`) passes. Rejected alternative (proposed during review): keep 1.85.0 and
`cargo update -p zune-jpeg --precise <older>` on aarch64 only. Not viable: the `foxglove` crate's own
remote-access code needs >= 1.88 regardless of zune-jpeg, no `zune-jpeg 0.5.x` compiles its NEON path
below 1.87, `image 0.25.9` requires `zune-jpeg ^0.5.5`, and the verifier restores the pristine
`Cargo.lock`, so a lockfile edit would also have to be replayed in the verifier image.
