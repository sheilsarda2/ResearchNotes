# Asynchronous parameter handling for the Foxglove C and C++ SDKs

You are working in `/workspace/repo`, a checkout of the Foxglove SDK monorepo at commit `b2fb3fab` (May 2026). The core SDK is Rust (`rust/foxglove`). The C SDK (`c/`) is a Rust crate (`foxglove_c`) that exposes an FFI surface; its header `c/include/foxglove-c/foxglove-c.h` is generated by cbindgen from `c/src` on every `cargo build` of that crate (`c/build.rs`). The C++ SDK (`cpp/foxglove`) is a hand-written wrapper over the C API.

The Rust core already ships an asynchronous, responder-based parameter API for both the WebSocket server and the remote-access gateway: the `foxglove::websocket::ParameterHandler` trait together with `GetParametersResponder` and `SetParametersResponder` (defined in `rust/foxglove/src/remote_common/parameters.rs`, registered through `WebSocketServer::parameter_handler` and `Gateway::parameter_handler`). The C and C++ SDKs only expose the older synchronous callbacks (`on_get_parameters` / `on_set_parameters` on `foxglove_server_callbacks` and `foxglove_gateway_callbacks`; `onGetParameters` / `onSetParameters` on `WebSocketServerCallbacks` and `RemoteAccessGatewayCallbacks`), which must compute their result inside the callback. Expose the responder-based API to C and to C++ so an implementation can hand a request to another thread and complete it later, for both the WebSocket server and the remote-access gateway.

## C API

All new C names are produced by cbindgen from `Foxglove*`-prefixed Rust types through `[export.rename]` entries, exactly like the existing entries in `c/cbindgen.toml` and `c/cbindgen.prelude.toml` (both files carry the rename table). The generated header must declare:

```c
typedef struct foxglove_get_parameters_responder foxglove_get_parameters_responder;  /* opaque */
typedef struct foxglove_set_parameters_responder foxglove_set_parameters_responder;  /* opaque */

typedef struct foxglove_parameter_handler {
  const void *context;
  void (*get)(const void *context, uint32_t client_id, const struct foxglove_string *request_id,
              const struct foxglove_string *param_names, size_t param_names_len,
              struct foxglove_get_parameters_responder *responder);
  void (*set)(const void *context, uint32_t client_id, const struct foxglove_string *request_id,
              const struct foxglove_parameter_array *params,
              struct foxglove_set_parameters_responder *responder);
} foxglove_parameter_handler;

void foxglove_get_parameters_responder_respond(struct foxglove_get_parameters_responder *responder,
                                               struct foxglove_parameter_array *params);
void foxglove_get_parameters_responder_drop(struct foxglove_get_parameters_responder *responder);
void foxglove_set_parameters_responder_respond(struct foxglove_set_parameters_responder *responder,
                                               struct foxglove_parameter_array *params);
void foxglove_set_parameters_responder_drop(struct foxglove_set_parameters_responder *responder);
```

and a new member `const struct foxglove_parameter_handler *parameter_handler;` appended as the **last** member of both `foxglove_server_options` and `foxglove_gateway_options`, so the offsets of all existing members are unchanged. The new declarations follow the existing header conventions (available outside `__wasm__`; gateway-specific declarations stay behind `FOXGLOVE_REMOTE_ACCESS`).

Contract:

- `request_id` may be NULL when the client sent none. `param_names` and `params` are never NULL and are valid only for the duration of the call; implementations must copy what they want to keep.
- The callee owns `responder` and must consume it exactly once with `*_respond` or `*_drop`, either synchronously inside the callback or later from any thread. `*_respond` takes ownership of `params` (a NULL `params` means an empty array; the array must have been created with `foxglove_parameter_array_create`). Passing a NULL responder must not crash: log an error and free `params`.
- The responders carry the core's semantics unchanged: a get response is sent to the requesting client; a set response is echoed to the requester only when the request carried a `request_id` and is never forwarded to other parameter subscribers (the implementer broadcasts applied updates with `foxglove_server_publish_parameter_values` / `foxglove_gateway_publish_parameter_values`, which may be called from inside the callback); consuming a responder with `*_drop`, or destroying it without responding, sends the core's generic error status to the requester (level error, message stating that the parameter handler failed to send a response). Parameters whose value is unset are dropped by the core before serialization.
- When `parameter_handler` is non-NULL on the options, the Parameters capability is advertised automatically (`FOXGLOVE_SERVER_CAPABILITY_PARAMETERS` / `FOXGLOVE_GATEWAY_CAPABILITY_PARAMETERS` need not be set) and the handler takes precedence over the legacy `on_get_parameters` / `on_set_parameters` callbacks, which are then never invoked. Subscribe/unsubscribe notifications continue to arrive through the legacy `on_parameters_subscribe` / `on_parameters_unsubscribe` callbacks.
- If `parameter_handler` is non-NULL but `get` or `set` is NULL, `foxglove_server_start` / `foxglove_gateway_start` return `FOXGLOVE_ERROR_VALUE_ERROR` without starting anything.
- Handler callbacks are invoked from time-sensitive contexts and must not block; document this, and document the legacy get/set callbacks as deprecated in favor of the handler.
- With no handler registered, the legacy callbacks keep their exact current behavior (including the automatic publication of the values returned by `on_set_parameters` to subscribers).

## C++ API

Add the public header `cpp/foxglove/include/foxglove/parameter_handler.hpp` and include it from `websocket.hpp` and `remote_access.hpp` so users of those headers see the types. In namespace `foxglove`:

```cpp
class GetParametersResponder final {
public:
  /// Send parameter values to the requesting client; consumes the responder.
  void respond(std::vector<Parameter>&& params) &&;
  ~GetParametersResponder() = default;
  GetParametersResponder(GetParametersResponder&&) noexcept = default;
  GetParametersResponder& operator=(GetParametersResponder&&) noexcept = default;
  GetParametersResponder(const GetParametersResponder&) = delete;
  GetParametersResponder& operator=(const GetParametersResponder&) = delete;
  // Not publicly constructible: instances are created by the SDK only.
};

class SetParametersResponder final {
  // Same shape: respond(std::vector<Parameter>&&) &&, movable, not copyable, SDK-constructed.
};

struct ParameterHandler {
  std::function<void(uint32_t client_id, std::optional<std::string_view> request_id,
                     const std::vector<std::string_view>& param_names,
                     GetParametersResponder&& responder)> onGet;
  std::function<void(uint32_t client_id, std::optional<std::string_view> request_id,
                     const std::vector<ParameterView>& params,
                     SetParametersResponder&& responder)> onSet;
};
```

`ParameterHandler` is a plain aggregate of those two `std::function` members (copyable and movable; a default-constructed one means "no handler"). `WebSocketServerOptions` and `RemoteAccessGatewayOptions` each gain a member `ParameterHandler parameter_handler;` appended after their existing members.

Contract:

- `WebSocketServer::create` and `RemoteAccessGateway::create`: if exactly one of `onGet` / `onSet` is set, return `FoxgloveError::ValueError` (log a warning; nothing is started). If neither is set, no handler is registered. If both are set, the handler is registered, which implies the `Parameters` capability and takes precedence over the legacy callbacks, as in the C contract. The handler and any legacy callbacks must remain valid for the lifetime of the created server/gateway object even though the options are consumed by `create`.
- `onGet` receives the request id (`std::nullopt` when absent) and the requested names in request order (empty means "all parameters"); `onSet` receives the parameters the client sent as `ParameterView`s. Both views and the `string_view`s are valid only during the call; implementations copy them out (`ParameterView::clone()`) to keep them.
- Responders: `std::move(responder).respond(values)` completes the request and consumes the responder; destroying a responder that was not responded to performs the drop (generic error status, as in the core). Responders can be moved into another thread and completed there. `respond` may throw `std::runtime_error` if the parameter-array allocation fails, leaving the responder intact (dropping it then sends the error status). Entries with unset values are dropped by the core.
- Calling `WebSocketServer::publishParameterValues` / `RemoteAccessGateway::publishParameterValues` from inside a handler callback is allowed and is the way to broadcast applied updates to subscribers (the set responder never does).
- If `onGet` or `onSet` throws, the exception must not propagate into the SDK: catch `std::exception`, report it through the SDK's `warn()` logger, and let the un-consumed responder be destroyed (which sends the error status). The connection stays usable.
- The legacy `onGetParameters` / `onSetParameters` members of `WebSocketServerCallbacks` and `RemoteAccessGatewayCallbacks` become `[[deprecated("...")]]` (message: use `ParameterHandler`; not invoked when a handler is registered) and keep working when no handler is registered. Users who do not touch those members, including moving options around or copying a `ParameterHandler`, must compile warning-free under `-Werror=deprecated-declarations`; the SDK's own sources that still read the legacy members must also compile warning-free (suppress locally).
- Update the doc comments of the legacy callbacks in both C and C++ to point at the new API.
