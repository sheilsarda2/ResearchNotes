## 3. Task-contract findings in the v2 pack

Three of my v2 tasks have hidden tests that pass only if the agent guesses something the instruction does not state (two are compile-time, one is error precedence), one anti-cheat pattern fails correct solutions (3e), and the three v1 durable-state tasks each have one or two sentences whose literal reading fails the hidden tests (3c, 3f). ### 3a. rs-zenoh hidden test imports an unnamed internal path

The first rs-zenoh trial (Opus, medium, 43 min, $17) failed at `build_a`: the hidden test binary did not compile.

```
error[E0432]: unresolved import `zenoh_protocol::network::timestamp_stack`
  --> zenoh/tests/timestamp_instrumentation.rs:171:34
```

The test `interception_point_try_from_valid` imports the constants `interception_point::{SEND, ROUTE, RECEIVE}` from `zenoh_protocol::network::timestamp_stack`. The instruction promises that tests import from `zenoh::timestamp_stack` and specifies the wire codes (0b001, 0b010, 0b100) but never names that module path in zenoh-protocol. Opus implemented `TimestampStack`, `InterceptionPoint`, `TimestampInstrumentationBuilder` and the `timestamp_stack()` accessors, i.e. the specified surface, and lost every hidden test to one compile error. This is the attribution failure the v2 Pugh chart scored as VER −1 for this task, now observed.

Recommended fix (not applied; changing a task mid-sweep changes its checksum): rewrite that one test to use the literal codes `1u8`, `2u8`, `4u8`, or add the exact module path to the instruction. Fixed in the v3 revision exactly this way (section 1b); the v3 campaign is 4 of 5. **Second occurrence in the original:** the Sonnet medium trial (54 min, 381 calls, $20.57) placed `pub mod timestamp_stack` in `zenoh/src/lib.rs`, exactly where the instruction says the tests import from, and failed on the identical `E0432`. Two trials, about $38, zero information. At 20 attempts across 9 cells this task will spend roughly $3k the same way; it should be excluded from the sweep until the test is fixed.

### 3b. rs-burn-store hidden tests need a `Debug` derive the instruction omits

The Sonnet trial's submission failed to compile the hidden unit tests with seven copies of:

```
error[E0277]: `PytorchReader` doesn't implement `Debug`
```

The hidden tests call `expect_err(...)` on `Result<PytorchReader, _>`, which requires `PytorchReader: Debug`. The gold patch adds `#[derive(Debug)]` to the struct; the pristine struct lacks it; the instruction's API listing shows `pub struct PytorchReader { /* private */ }` with no derive. Fable and Opus happened to add the derive and compiled. Sonnet's zero is deserved on other grounds (see section 5), so no trial has yet been wrongly failed by this, but any correct solution without the derive will be. Fix: add the derive to the instruction's API listing, or change the hidden tests to `assert!(result.is_err())` and match on the error. Same checksum caveat as 3a.

### 3d. rs-burn-store hidden test pins error precedence on a doubly malformed fixture

Both Opus trials on rs-burn-store (medium, $10; high, $21) failed exactly one of 108 hidden unit tests, `test_tar_absurd_storage_count_is_an_error`, with every other group green (fixture matrix 62/62, reject cases 32/32). The test builds a TAR containing `storages` (a count pickle claiming 2^40 storages), `tensors` and `pickle`, and no `sys_info` entry. It requires `Err` whose message contains "Pickle". The instruction (section 3.4) lists `sys_info` as a TAR entry and requires `little_endian` to be true in it; Opus checked the container first and returned `Invalid PyTorch file format: TAR archive has no 'sys_info' member`, a correct rejection of a malformed file. The test therefore pins the gold's parse order (read `storages` before validating `sys_info`), which nothing in the instruction states. Fix: add a valid `sys_info` entry to the fixture so the absurd count is its only defect, or accept any `Err`. Same checksum caveat. Two trials wrongly failed, about $31.

### 3e. rs-burn-store anti-cheat regex fails a fully correct solution

In the burn-reader-v4 campaign, Sonnet at high effort passed every test group: 108 of 108 hidden unit tests, 52 safetensors, 20 integration, 37 pytorch-tests crate, 62 of 62 fixture-matrix, 32 of 32 reject cases. Reward 0, because the anti-cheat group flagged one line:

```
crates/burn-store/src/pytorch/pickle_reader.rs:2169: .join("src/pytorch/tests/reader/test_data/non_contiguous.pt");
```

The verifier's forbidden-pattern list includes the bare string `/tests/`, meant to catch references to the verifier's own `/tests/` mount. It also matches the repository's in-source fixture directory `src/pytorch/tests/reader/test_data/`, which the pristine crate ships and which a unit test written inside `src/` legitimately loads. One wrongly failed trial ($16, 16 minutes); the earlier Sonnet-medium v4 trial had the same hit but also failed tests. Fix: anchor the pattern to the absolute mount (`(^|["'\s])/tests/`) or exclude `src/pytorch/tests/`. Audit of the other v2 verifiers: rs-zenoh's anti-cheat also counts the bare string `/tests/` (against pristine counts, so only an increase flags) and its upstream has an in-source `src/replication/tests/` directory; rs-rerun's upstream has `src/importer_mcap/tests/` but its verifier does not grep for the bare pattern. The v1-style tasks and the other v2 tasks do not use it. So the fix is needed in rs-burn-store (all versions) and is worth applying defensively to rs-zenoh v3.

### 3f. The Fable failures on luigi and huey are reading differences, not engineering errors (audit done)

I pulled the assertion diff for every failing trial of the two recurring tests.

**luigi `test_retention_order_and_validation`, 9 failing trials.** Six (all Fable, medium and high) fail with "Right contains one more item": after five publishes, `prune(keep=3)` removed one generation where the test expects two. The instruction says prune "retains the current generation, the newest `keep` committed generations, every actively pinned generation, and active staging writers". Read literally that is current plus three, four kept, one removed, which is what Fable built. The test treats the current generation as one of the `keep`. Two more Fable failures raise `TypeError: keep must be a nonnegative integer, got 1.5` where the test demands `ValueError`; the instruction says "`keep` must be a nonnegative integer (not bool)" and names no exception. The remaining failure (Opus once, Sonnet once) is a different assertion about writer generation identity. Fable's 1 of 9 on luigi is therefore mostly two defensible readings of two sentences. Fix: "retains the newest `keep` committed generations, counting the current one" and "raises `ValueError`".

**huey `test_context_renewal_and_stale_execution`, 15 failing trials.** Nine Fable and one Opus fail on the test's first assertion, `h.execute(t) == t.lease_token`: the task body returned the token it saw via `task.lease_token`, but the dequeued `t.lease_token` is `None` after `execute` returns. The instruction says "`Task.lease_token` exposes that token (or `None` for an unreserved task)" and, elsewhere, that "a normal return ... acknowledges the reservation". Fable consistently sets the token to `None` once the reservation is acknowledged, which is a literal reading of those two sentences together; the test expects the Task to keep its last token. One Fable trial also shows renewal minting a new token string (suffix `.1`), where the test expects renewal to keep the token's identity; the instruction says renew "extends its expiry" and does not say whether the token changes. Sonnet's five failures are different and genuine: `DID NOT RAISE LeaseLost`, it let an expired task run. Fix: "the Task keeps its token after acknowledgement" and "renewal keeps the same token".

**Consequence for the picks.** The model asymmetry that made huey and luigi look like the informative band (Opus 10 of 12 and 6 of 9; Fable 1 of 9 and 1 of 12) is largely wording. With the four sentences fixed, Fable's rates rise toward Opus's, and both tasks move toward the saturated group for Opus and Fable, with Sonnet the only model still failing on genuine grounds. Their zeros were mostly measuring the instruction, the same finding as schema-plan (3c), now across all three v1 durable-state tasks.

### 3c. sqlite-utils-schema-plan (v1): one unstated edge case decides a fifth of its trials

Across 32 schema-plan trials (pilot and sweep, all three models, 0 passes), `test_default_values_are_literals[a\x00b]` fails in 25. The test sets a column default to a string containing a NUL byte. Python's sqlite3 refuses SQL text containing NUL, so the gold special-cases it: `(CAST(X'<hex>' AS TEXT))`. The instruction's defaults rule says "All strings are literal values, including `CURRENT_TIMESTAMP`, `NULL`, quotes and parentheses" and never mentions NUL bytes. Of the 30 failed trials with logs, 3 failed only that test and 6 failed only it and/or `test_plan_validation_is_atomic[bad18]` (a column both dropped and listed in `column_order`, also not spelled out); 15 of 27 failed three or fewer of the 332 tests. The task's zero pass rate is therefore mostly a long tail of one-to-three edge cases, with the NUL default the largest single contributor. This is the "over-specified" risk the v1 chart flagged, now measured: fix by naming NUL handling in the instruction (a line and an example), or by dropping that parameter from the test.
