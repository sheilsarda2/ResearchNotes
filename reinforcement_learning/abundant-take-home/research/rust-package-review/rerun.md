## 1. Exact rows when saving the selected time interval

**Demand match: strong and narrow; prevalence unknown.** In [#12596](https://github.com/rerun-io/rerun/issues/12596), January 27, 2026, `nathan-b-flya` supplies C++ code and recordings: selecting steps 4–7 and saving exports the original data. Another selection exports an entire pose stream. This is one affected reporter, not several independent users. They [confirm the same problem in real data](https://github.com/rerun-io/rerun/issues/12596#issuecomment-3811458713), with different excess intervals per stream. The consequence demonstrated is inaccurate exported recordings; business loss or widespread adoption is not established.

Maintainer Wumpf [identifies whole overlapping chunks as the cause](https://github.com/rerun-io/rerun/issues/12596#issuecomment-3810831112), January 28: “it should truncate all chunks in the range.” The reporter's [February 3 workaround](https://github.com/rerun-io/rerun/issues/12596#issuecomment-3841776767) sets `RERUN_CHUNK_MAX_ROWS=1` before opening the viewer, exports, then optionally compacts the output. Fixing row selection directly addresses that workflow without asking the user to change chunking.

**Current behavior:** main's [`EntityDb::to_messages`](https://github.com/rerun-io/rerun/blob/ddd684110e1f200ee13ba482ab42689b78dd0551/crates/store/re_entity_db/src/entity_db.rs#L1036) still tests chunk/time-range intersection and clones whole chunks. Its explicit slicing TODO remains. The method promises selected timeline/range data and is the headless export boundary, so no UI automation or C++ dependency is needed to test this Rust contract.

**CONFIRMED on pinned current main:** [the Rust reproduction](reproductions/rerun/time_selection.rs) compiled and executed successfully, then failed its intended-behavior assertion ([complete log](reproductions/rerun/time_selection-main.log)). A single temporal chunk contains steps 2,4,…,20 plus a separate static row. Full-export and disjoint-range controls passed, retaining static data; the source-immutability assertion also passed. Selection [4,7] returned all ten temporal rows instead of [4,6]. Cargo exit 101 is the expected failing assertion, not a build error. Test execution took 0.01 seconds. Exact environment and command are in [reproduction metadata](reproductions/rerun/time_selection-main.json). An earlier invocation found rustfmt absent in the stock image; formatting was not claimed, and the final direct cargo invocation completed. No implementation was patched.

**Already fixed or in progress?** Exact-issue all-state PR search returned zero; its issue timeline contains labels/comments, no linked commits or PRs. All 18 open PRs and the 100 most recently updated closed PRs were reviewed by metadata; broader all-state time-selection/time-slice searches were examined. - [#11318](https://github.com/rerun-io/rerun/pull/11318), closed unmerged, proposed cropping incoming server data and handling overlapping loads; it did not implement selected export.

No exact active implementation was identified in this bounded public search. This cannot exclude private work or a differently named unlinked branch.

**Bounded task design:** make selected `EntityDb::to_messages` export retain only rows whose chosen timeline lies in the selected closed integer interval, while retaining all static data, complete columns for selected rows, original row IDs, valid independent chunk metadata, store information, and blueprint activation behavior. Preserve the existing floor(min)/ceil(max) conversion rather than inventing a new fractional-time contract. Export must not mutate source data. Tests should cover sorted/unsorted timestamps, both boundaries, multiple entities/chunks/timelines, sparse components, all/none overlap, source immutability, and Arrow encode/decode round trips. Existing `Chunk::filtered` already aligns all columns and creates fresh chunk IDs; this may be a modest integration fix. **No claim that it naturally requires 75+ actions.**

## 2. Shutdown with a large queue and unavailable gRPC endpoint

**Demand match: concrete, but current Rust-only execution still pending.** [#12821](https://github.com/rerun-io/rerun/issues/12821), June 18, 2026, reports C/C++ SDK cleanup exceeding a 60-second watchdog after one million per-row scalar logs. A small input and the same million rows through `send_columns` return in roughly six seconds. The affected workflow is process/recording teardown when its configured viewer endpoint is unavailable. A [separate Python reporter, #12620](https://github.com/rerun-io/rerun/issues/12620), February 7, reports process exit blocked until starting the viewer. This supports the general teardown failure, but is not a second report of the exact million-row C fixture.

**Current release reproduction:** [shutdown_probe.py](reproductions/rerun/shutdown_probe.py) ran against `rerun-sdk==0.37.2` with a closed local loopback endpoint. One row returned after 3.04 seconds from the shutdown marker; one million columnar rows returned after 3.09 seconds. One million row-log calls exceeded the separate 20-second shutdown watchdog and were killed. Logging completed before that watchdog began. [Full output](reproductions/rerun/shutdown_probe-0.37.2.log). This establishes **greater than 20 seconds**, not infinite blocking. It exercises the Python binding and underlying Rust SDK, not the exact C free function or a fresh main Rust build.

Main still has an unlimited batcher flush and thread join in [`RecordingStreamInner::drop`](https://github.com/rerun-io/rerun/blob/ddd684110e1f200ee13ba482ab42689b78dd0551/crates/top/re_sdk/src/recording_stream.rs#L886). Exact-issue PR search returned zero and the timeline contains no linked fix. Open [#12846](https://github.com/rerun-io/rerun/pull/12846) hardens server-backed DataFusion chunk fetching; its files do not address SDK shutdown. Historical [#11008](https://github.com/rerun-io/rerun/pull/11008), merged August 28, 2025, deliberately made normal flush waits unlimited while promising early exit for disconnected gRPC. A task must preserve successful slow flushes and target unavailable-endpoint shutdown; imposing a blanket short timeout risks reintroducing lost-data behavior. That contract and the heavier execution harness make this a weaker immediate task choice than #12596.
