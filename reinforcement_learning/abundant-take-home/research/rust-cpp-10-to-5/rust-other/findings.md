## Recommendation

1. **object_store #806 — advance as a concrete compatibility repair.** Strong exact downstream demand and a current-main failure with three working controls. Natural implementation scope may be modest; this is not evidence of long-horizon difficulty.
2. **arrow-rs #7982 — strongest substantial reserve, with an explicit public-work caveat.** Current Rust schema representation drops dictionary-value extension metadata in a real GeoArrow interoperability workflow. C Data preservation can be bounded independently, but adjacent IPC/format work has a public maintainer commitment. Do not claim the entire problem is unclaimed or that metadata preservation is mandatory in the C Data specification.
3. **Tantivy #2666 — prune from the top five.** A stale public commit-opstamp accessor is real and downstream demand is documented. The current code does *not* reproduce the report's rollback corruption mechanism: rollback reconstructs the writer from current committed metadata. A task based on the broad report would overstate the verified defect. A narrow accessor/commit-state task appears modest.

## 1. object_store: full-object range responses with HTTP 200

- **Primary report:** [object_store #806](https://github.com/apache/arrow-rs-object-store/issues/806), with reporter follow-up [asking contributors to investigate](https://github.com/apache/arrow-rs-object-store/issues/806#issuecomment-5309625281).
- **Exact demand:** [Polars #28400](https://github.com/pola-rs/polars/issues/28400) reports small Parquet files failing over miniserve while larger files on the same server read successfully. The request for the small file covers its entire byte range; miniserve returns the complete representation as 200. This is a concrete user workflow and has the Polars upstream-issue and medium-priority labels. The separate cifzarr #35 reference says explicitly that #806 is adjacent, not its own blocker; do not count that report as exact demand.
- **Source:** `apache/arrow-rs-object-store` HEAD `279572ea60f3a7a6e5237e066a6f4a35eee611e0`, package 0.14.2, MSRV 1.85. Latest release observed: v0.14.1; release was not separately executed.
- **Current code:** [get_request](https://github.com/apache/arrow-rs-object-store/blob/279572ea60f3a7a6e5237e066a6f4a35eee611e0/src/http/client.rs#L404) rejects every non-206 response if the caller supplied a range. The [HTTP Range contract](https://www.rfc-editor.org/rfc/rfc9110.html#name-range) allows a server to ignore Range; the requested compatibility behavior is justified when the full returned representation is sufficient for the caller's requested whole-object range.
- **Executed result:** [object_range-main.json](probe/object_range-main.json) records the actual current Rust API's failure for a full-range 200 with a 12-byte body. Plain 200, partial-range 206, and full-range 206 succeed. A 200 that ignores a true subrange remains an error, providing a regression control against simply accepting every 200.
- **Scope:** Support the report's whole-object 200 response while maintaining correct bytes, range and object-size metadata and existing true-subrange rejection. A local server makes independent tests deterministic and offline. Include full response both with and without stray Content-Range, normal 206, wrong-size/full-body mismatch and retried reads as justified by affected pathways. Do not broaden into unrelated S3/GCS fixes.
- **Fix search:** All 21 current open PRs, issue comments/timeline, and searches `repo:apache/arrow-rs-object-store is:pr 806` and `repo:apache/arrow-rs-object-store is:pr "range" "200"` were saved. No exact fix found. The one related match [#609](https://github.com/apache/arrow-rs-object-store/pull/609) repairs EOF retry duplication and adds retry response validation; it does not allow the current initial full-range 200 response. Its actual diff was inspected.
- **Natural effort:** Likely small-to-medium Rust change spanning HTTP response validation and common range metadata, with meaningful regression tests. This may fall short of the take-home's desired long horizon; no agent-step count or model difficulty was measured.
- **Limits:** Probe uses a minimal loopback HTTP server that reproduces the reporter's response, not the actual miniserve executable or a full Polars/Parquet read.

## 2. arrow-rs: preserve dictionary-value extension metadata

- **Primary report:** [arrow-rs #7982](https://github.com/apache/arrow-rs/issues/7982). The reporter's actual stack is arro3, GeoArrow, nanoarrow and PyArrow. A dictionary of WKB extension values loses its extension name and serialized metadata after conversion through Rust. The report explains that Parquet readers may return dictionary encoding outside the application's control.
- **Related demand:** A maintainer independently encountered the representational limitation while implementing nanoarrow IPC support and references the Rust gap in [Arrow #49704](https://github.com/apache/arrow/issues/49704). That report demonstrates that dictionary-of-extension and extension-with-dictionary-storage are distinct and C Data can represent both.
- **Source:** `apache/arrow-rs` HEAD `4cd8be954f6bc6b6dd265140207365b59a9900ec`, package 60.0.0, MSRV 1.88. Latest release observed: 59.3.0; release was not separately executed.
- **Current code:** The dictionary import [uses DataType, losing the value field's metadata](https://github.com/apache/arrow-rs/blob/4cd8be954f6bc6b6dd265140207365b59a9900ec/arrow-schema/src/ffi.rs#L710). `DataType::Dictionary` stores boxed data types, not value fields. Metadata on the outer Field cannot represent the distinction transparently.
- **Executed result:** [arrow_metadata-main.json](probe/arrow_metadata-main.json) imports a C Data dictionary schema with `ARROW:extension:name=geoarrow.wkb` and `ARROW:extension:metadata={}` on the dictionary values, converts it through `Field`, then exports it. The resulting dictionary metadata is empty. The identical metadata survives the scalar-field roundtrip control. Only schema import/export was executed, not a complete populated dictionary array or PyArrow/GeoArrow process.
- **Scope:** Extend the Rust schema representation and its C Data import/export to retain dictionary-value metadata distinctly from parent metadata, through nested fields and ordinary cloning/equality. Preserve existing dictionary behavior. Construction must make a clear API compatibility choice and exercise real array/type integration where the chosen representation requires it. Merely retaining a sidecar outside the Rust schema would not meet the user's stated interoperability gap. No particular enum design or arbitrary set of changed files is prescribed.
- **Natural effort:** Potentially substantial schema and integration work. There are 81 source files mentioning `DataType::Dictionary` in the current checkout; that is a dependency-surface observation, not 81 required modifications or a difficulty measurement. `arrow-schema` alone is tiny to compile; testing array integration will require more of the Arrow workspace. A full workspace build has not been measured.
- **Fix search and work caveat:** All current open Arrow Rust PRs (pagination followed), issue comments/timeline, and exact issue/dictionary-extension searches found no matching *Rust C Data representation fix*. However, [Arrow C++/format #49704](https://github.com/apache/arrow/issues/49704#issuecomment-4686991120) has an explicit maintainer commitment to implement adjacent IPC work. The [April 14 mailing discussion](https://lists.apache.org/thread/4xj0yrl2vn0lbrv39p3dvd28okvkjxyz), saved in `sources/arrow-format-thread.json`, chooses adding metadata to IPC's DictionaryEncoding. This neither changes the current Rust `DataType` nor fixes the current probe, but any broad task covering IPC would overlap that public work. Under a rule that excludes even adjacent claimed format work, prune this candidate.
- **Contract caution:** The [C Data specification](https://arrow.apache.org/docs/format/CDataInterface.html#c.ArrowSchema.metadata) permits consumers to ignore metadata. This is a requested feature/interop gap, not proof of violating a mandatory conformance rule. Demand comes from the reported workflow, not from inventing stronger specification language.

## 3. Tantivy: stale committed-opstamp accessor

- **Primary report:** [Tantivy #2666](https://github.com/quickwit-oss/tantivy/issues/2666).
- **Exact downstream demand:** [tantivy-go #24](https://github.com/anyproto/tantivy-go/pull/24) explicitly disabled rollback in a shipped workaround citing this issue; [Anytype #2547](https://github.com/anyproto/anytype-heart/pull/2547) describes full-text consistency recovery, opstamp tracking, and users seeing inconsistent indices. This demonstrates people acted on the exact issue, but does not make all the report's causal claims correct on current upstream.
- **Source:** `quickwit-oss/tantivy` HEAD `4abd98fa19a75671a08631190ca90d93b9dbd2df`, package 0.27.0, MSRV 1.87. Latest release observed: 0.26.1; release was not separately executed.
- **Executed result:** [tantivy_opstamp-main.json](probe/tantivy_opstamp-main.json) shows actual commit stamp 2 but `commit_opstamp()` returns 0. The rollback control returns 2, keeps the committed document, and restores the stamper from the committed index. The report's claim that current rollback blindly resets the stamper to 0 is false for this current path.
- **Source confirmation:** [rollback reconstructs IndexWriter](https://github.com/quickwit-oss/tantivy/blob/4abd98fa19a75671a08631190ca90d93b9dbd2df/src/indexer/index_writer.rs#L565); [commit_opstamp returns a cached field](https://github.com/quickwit-oss/tantivy/blob/4abd98fa19a75671a08631190ca90d93b9dbd2df/src/indexer/index_writer.rs#L730). `delete_all_documents` also uses the field, but that path and any resulting data loss were not executed in this audit.
- **Scope if retained:** Correct reporting of the last successful committed stamp across regular/prepared/asynchronous commit completion while retaining rollback semantics. Failed or merely prepared commits must not advance the reported committed stamp. Avoid bundling separate pending-delete issues to inflate the task.
- **Fix search:** Issue timeline/comments and `is:pr "opstamp"` search found no exact upstream fix. Actual diffs of open [#2999](https://github.com/quickwit-oss/tantivy/pull/2999) and [#2682](https://github.com/quickwit-oss/tantivy/pull/2682) change adjacent commit machinery but do not synchronize the cached field. A [public fork characterization #9](https://github.com/teamleaderleo/tantivy/pull/9) expressly compensates for #2666 to isolate a *different* pending-delete defect; it is not an upstream fix for the accessor.
- **Natural effort and pruning reason:** A narrow, probably modest state-reporting repair remains; current evidence does not substantiate the broad data-corruption task. Prefer stronger naturally integrated candidates for the final five.

## Arrow construction decision after exact-constructor review

Arrow remains reserve, not selected for construction. Current [arro3 source](https://github.com/kylebarron/arro3/blob/d65a1a5eeee0af3a0e292111ed077c0c181fb7fc/pyo3-arrow/src/datatypes.rs#L518) stores only a Rust `DataType`, imports Python inputs through `DataType::try_from`, constructs the existing `Dictionary(Box<DataType>, Box<DataType>)`, and exports by creating a fresh `Field`. Therefore a Field metadata sidecar could pass the earlier schema probe without repairing the original constructor example. Changing only Dictionary's second argument to FieldRef would break downstream construction and still lose scalar extension metadata before construction.

A fair exact contract would have to preserve extension metadata at standalone DataType import, preserve it when the existing dictionary constructor nests the imported type, and export it again through a newly created Field; additionally, dictionary and extension-with-dictionary-storage must remain distinct. That implicates general DataType representation, exhaustive matches across the Arrow workspace, and a pinned arro3 consumer integration. It should not be presented as a small FFI patch or constrained to Field import/export alone. A narrower Arrow schema enhancement is possible, but it would not establish the reporter's complete requested use case. The final pool retains the measured gap and public-work caveat; the immediate implementation selection chooses the better bounded object_store task instead.
