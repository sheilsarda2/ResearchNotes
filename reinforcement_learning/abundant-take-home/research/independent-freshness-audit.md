**SQLite schema planner: substantial partial overlap, plus a new runtime caveat.**

Confirmed upstream functionality: native column renaming already updates dependent indexes, triggers and views, and rejects ambiguous rewrites. Native DROP rejects referenced columns. SQLite also publishes a transactional table-rebuild procedure that saves and recreates dependent objects. These are implementation building blocks; neither dependency-aware renaming nor the general rebuild strategy is an original algorithm of this task. [SQLite ALTER TABLE documentation, inspected September 13](https://www.sqlite.org/lang_altertable.html).

The material addition to the existing provenance is **SQLite 3.53.0, released April 9, 2026**. Its release notes explicitly add ALTER support for NOT NULL and CHECK constraints; the current ALTER documentation describes SET/DROP NOT NULL. The latest release history lists 3.53.4 on July 24. The candidate's recorded container uses SQLite **3.40.1**, so its requirement to implement nullability changes through older-runtime facilities is partly a compatibility exercise. Do not say that current SQLite generally cannot alter nullability. This does not supply the candidate's type-conversion rules, column order/default changes, simultaneous renames, isolated validation preview, or complete multi-table API. [3.53.0 release notes](https://www.sqlite.org/releaselog/3_53_0.html), [current release history](https://www.sqlite.org/changes.html).

The public implementation in [PR703](https://github.com/simonw/sqlite-utils/pull/703), opened January 21, 2026 and still open, adds incoming-FK updates to `transform()` and the CLI, including self-references and execution in a transaction. Its current file patches were fetched in this audit. That behavior must be treated as a public partial solution, even though it is unmerged. Its scope does not implement the current `transform_schema` contract. The PR also attributes commits to `claude`; that is authorship evidence, not a measured trial or model/harness result.

[PR854](https://github.com/simonw/sqlite-utils/pull/854), opened September 6, is confirmed **documentation-only**: its sole changed file is `docs/python-api.rst`. Its author reports current-main checks showing index reconstruction, retained views, and deleted table triggers, and supplies a capture/reissue recipe with a renamed-column caveat. Those behavioral reproductions remain the author's reports in this independent audit; I did not rerun them. [PR861](https://github.com/simonw/sqlite-utils/pull/861), opened September 13, is another one-line documentation correction, also not a feature implementation. Do not interpret either PR's wording as evidence that all dependent objects are already repaired. [PR499](https://github.com/simonw/sqlite-utils/pull/499), opened October 11, 2022, separately offers FTS trigger recreation. Exact metadata and changed-file patches for 703/854/861 are in [PR details](sources/independent-freshness-pr-details.json).

**Decision:** keep the full composed schema contract for screening, but describe it as coordinated, lossless transformations on the specified runtime. Remove any pitch centered on inventing dependency-aware rename or NOT NULL alteration. Changing the frozen runtime is not required by this finding; any later runtime change should be a new verified pack version. This audit does not establish whether public building blocks make the full task short.

**DiskCache: current PRs, forks and backup lookalikes.**

The independent API fetch found **27**, not the earlier provenance's 25, open PRs. The two newest are [Deque self-extension #370](https://github.com/grantjenks/python-diskcache/pull/370), September 11, and [unlimited Deque maxlen #369](https://github.com/grantjenks/python-diskcache/pull/369), September 8. The word “snapshot” in #370 describes copying a deque's original values for self-extension, not a consistent cache backup. The 27 fetched titles/bodies contain no implementation claim matching either candidate; this is an inventory result, not a search of every branch.

Fork coverage was expanded beyond the earlier audit: from the newest 100 listed forks, I scanned the default-branch source archives of the 22 with a 2026 push date, plus `diskcache2`, `havocesp/python-diskcache`, typed-diskcache and diskcache_rs. Most sampled recent fork default branches still equal upstream; feature work may live on other branches. Archive roots, SHA-256 hashes, file counts and lexical matches for reshard/snapshot/backup/migrate/restore are saved in [fork scan](sources/independent-freshness-diskcache-forks.json). Relevant source files are in [fork details](sources/independent-freshness-fork-details.json). A guessed `wandb/diskcache` archive URL returned 404; PyPI's actual `diskcache-weave` source distribution was subsequently inspected instead. Older forks, all non-default branches, alternate feature names and unpublished work remain outside coverage.

**Decision:** keep both DiskCache candidates. For online reshard, the substantive distinction is persisted topology plus bounded migration and mutation reconciliation; for snapshots it is the consistent database/payload set, validation and publication. Neither all-shard transactions nor ordinary directory/database copying is new. The actual reshard instruction permits live writes, while `workflow-candidates.md` still describes the superseded write-blocking proposal and says not to promise online writes. Mark that older document historical or update its status before sharing the pilot pack.

**Current model results that constrain the difficulty story.**

The strongest directly adjacent counterexample remains the current [FrontierSWE v2 flash-filesystem task](https://www.frontierswe.com/tasks/flash-fs): Fable 5 scores **0.9709 ± 0.046**, averaging 481 steps and 15.6 hours; Opus 5 scores 0.8559 and Fable 5.1 0.7779. It tests crash recovery and exact disk state. These are published composite scores, not binary solve rates. The September 8 [changelog](https://www.frontierswe.com/changelog) records adding Fable 5 and Opus 5. Quoting only a lower-scoring model would hide strong counterevidence to “durability is beyond current models.”

The current [SWE-Marathon v1.1 publisher bundle](https://swe-marathon.vercel.app/assets/index-r_3Fj-TG.js), parsed as data without executing its JavaScript, supplies more specific counterexamples than aggregate leaderboard scores:

- `zstd-decoder`: Fable 5.1/max, Claude Code, **8/8**, trials dated September 4, with recorded steps **31–62**. GPT-6 Astra/max, Codex, also has 8/8. A substantial technical specification need not produce a >75-step solution.
- `kubernetes-rust-rewrite`: GPT-6 Astra/low, Codex, **8/8**, September 8; the max configuration reports **1/8**, September 4. These are separate configurations/dates, not a controlled causal experiment on effort. They show why a weaker result at one effort does not establish strongest-configuration headroom.
- `biofabric-rust-rewrite`: Astra/max reports **0/8** despite a 0.986 partial score. The publisher labels partial scores uncalibrated. A binary zero requires failure inspection; it cannot automatically be described as little engineering progress.

Selected configurations and all their published trial records are preserved with the official bundle URL/hash in [Marathon task results](sources/independent-freshness-marathon-task-results.json). I did not rerun or independently validate these submissions. Published step counts use their publisher's harness convention, not this pack's ATIF counting convention. The results concern different tasks and budgets; they measure neither our success rate nor our necessary horizon.

For balance, [FrontierSWE's PostgreSQL-on-SQLite task](https://www.frontierswe.com/tasks/postgres-sqlite-wire-adapter) still tops out at 0.3429 on its current table. Its entire server/protocol translation scope, test-fraction score and 20-hour budget differ greatly from these Python features. Its lower result cannot be transferred to the schema planner or relational merge. The [v2 methodology](https://www.frontierswe.com/blog/v2) also changes task visibility, grading and the harness, so v1/v2 comparisons require version context.

Finally, [SWE-Refactor-Bench PR9](https://github.com/Einsia/SWE-Refactor-Bench/pull/9) was **merged September 10 at 09:39:45 UTC**. The maintainer's [09:44 comment](https://github.com/Einsia/SWE-Refactor-Bench/issues/8#issuecomment-5616543994) confirms four reproductions and says fw05 published scores were depressed and would be rerun. That correction is confirmed; open reports about other graders remain reports. This audit did not establish a new corrected fw05 leaderboard score. Low aggregate acceptance still does not independently establish these candidates' hardness.

The pilot decision should rest on validated candidate verifiers and actual per-task trajectories. None of the negative searches here proves that an exact public solution does not exist, and none of the positive adjacent benchmark results establishes saturation of these ten contracts.
