# Workflow and cache feature candidates

Initial design notes, researched 2026-09-13. **Historical proposal:** the current [candidate instructions](../candidates/README.md) and [shortlist](shortlist.json) supersede the proposed APIs, implementation estimates and construction status below. Reference implementations and Harbor validation were subsequently added; model headroom and the required >75-step horizon remain unmeasured. The initial research involved no model or paid API calls.

The reshard proposal below blocked writes during migration. The final [online reshard contract](../candidates/diskcache-online-reshard/instruction.md) instead permits live managed-client writes and requires durable mutation reconciliation, pause/resume and bounded migration work. Its implementation and verifier must be assessed against that final contract, not this earlier write-blocking design. See the [independent freshness audit](independent-freshness-audit.md) for current upstream, fork and benchmark counterevidence.

Repositories were cloned from their current public default branches into `research/cache/`. Luigi is pinned to `715f65c4a56a908ef0a1df4df6fc33b8420e2e6c` (2026-07-18); DiskCache is pinned to `ebfa37cd99d7ef716ec452ad8af4b4276a8e2233` (2024-03-02). Each candidate should be an independent Harbor task starting from its listed base, with its own solution and hidden verifier.

## 1. luigi-generation-target

**Feature:** atomically publish, read, and retire a named collection of local output files as immutable generations.

**Why this is absent:** Luigi explicitly documents that multiple output targets can lose atomicity. Its local atomic writer calls `os.replace` for one file; `temporary_path()` stages one filesystem target. Neither provides generation identity, collection integrity, compare-and-swap publication, or pinned readers. Existing directory staging is useful prior art, so simply adding an atomic directory target would be insufficient novelty. See the pinned [task documentation](https://github.com/spotify/luigi/blob/715f65c4a56a908ef0a1df4df6fc33b8420e2e6c/doc/tasks.rst#L55-L62), [local target implementation](https://github.com/spotify/luigi/blob/715f65c4a56a908ef0a1df4df6fc33b8420e2e6c/luigi/local_target.py#L34-L43), and [temporary-path implementation](https://github.com/spotify/luigi/blob/715f65c4a56a908ef0a1df4df6fc33b8420e2e6c/luigi/target.py#L269-L304).

**Proposed public contract:** add `luigi.LocalGenerationTarget(root, members)` where `members` maps logical names to relative paths. Add `write(expected_generation=...)`, `snapshot()`, `current_generation`, `exists()`, and `prune(keep=...)`. A writer context exposes `open(name, mode)` and publishes automatically only on successful context exit. A snapshot exposes an immutable generation ID and `open(name, mode='r')` and must be closed or used as a context manager.

- All required members must have been written and closed before publication. Missing members, duplicate normalized paths, escaped paths, symlinks, an open write handle, or an exception abort publication. Nested directories and binary content are supported. Empty collections are rejected.
- A generation contains a versioned manifest with logical names, relative paths, sizes, and SHA-256 digests. The current-generation pointer changes atomically only after a complete generation is durable. Readers see a complete old or complete new generation; interruption must never expose a partial file set.
- `exists()` is true only for a committed, structurally valid generation whose members satisfy its manifest. Missing output and corruption return false; explicit snapshot opening raises a documented integrity exception with the affected member. Permission and unrelated I/O errors remain distinguishable from absence.
- The default writer captures the current generation when opened. At publication it compares that identity again while serialized with other publishers. Exactly one of two writers opened against the same generation can publish; the other raises a documented conflict. An explicit expected ID provides the same condition; an explicitly documented unconditional mode may be supported but must not be the default.
- Snapshot identity remains stable while later generations are published. `prune(keep=N)` retains the current generation, the newest N committed generations, and any live pinned snapshots. It must not delete an active staging writer or follow links outside the root. OS-released locks allow recovery after a reader/writer subprocess dies. Scope is a local POSIX filesystem; network filesystem and Windows guarantees need not be invented.
- Ordinary `LocalTarget`, format handling, and `Task.complete()` semantics remain compatible. Include a real Luigi task whose output is the new target and a downstream task that reads a snapshot.

**Deterministic hidden verification:** compare contents and digests for several randomly seeded member sets; test failed and incomplete writes; pin generation A, publish B, prune, and prove A remains readable until unpinned; coordinate two writers with multiprocessing pipes to test conflict behavior; terminate a staging writer and separately interrupt pointer replacement using documented OS-call patching; reopen in a new interpreter; corrupt a member and manifest; test nested names, traversal, symlinks, format/binary behavior, and normal LocalTarget regression. No timing-dependent sleeps or external services are necessary. Tests should assert public behavior rather than prescribe the private directory layout beyond the public manifest contract.

**Oracle feasibility:** a reference implementation can use staging directories, fsync, a short publication lock, atomic pointer replacement, immutable manifests, and per-generation shared reader locks. This is several interacting mechanisms across target behavior, lifecycle management, and tests. Avoid a reference solution that merely writes a success marker after multiple output files: interruption between member writes and reader use would remain observable. A complete oracle plus upstream targeted regressions must pass before calling this runnable.

**Public solution check:** searches for Luigi generation/manifest targets and `GenerationTarget` did not surface the full contract. Initial retrieval of PR #1066 was rate limited. The independent September 13 audit subsequently inspected [PR1066](https://github.com/spotify/luigi/pull/1066): it proposed directory output staging in July 2015 and closed unmerged that September. It is concrete adjacent prior art, not the full generation/pinning contract. Current source and documentation supply the positive evidence for what upstream does. Absence from these bounded searches is not proof that no public implementation exists anywhere.

## 2. luigi-checkpoint-task

**Feature:** explicit durable task state transitions that retain discovered dynamic dependencies across worker restarts.

**Why this is absent:** upstream docs require dynamic `run()` code to be idempotent because it resumes from the beginning when yielding an incomplete dependency. `TaskProcess._run_get_new_deps()` calls `self.task.run()` afresh, returns serialized dependency identities, and does not persist an application-state cursor. Scheduler persistence and task-output markers solve different problems. See [current dynamic dependency documentation](https://luigi.readthedocs.io/en/latest/tasks.html#dynamic-dependencies) and [pinned worker code](https://github.com/spotify/luigi/blob/715f65c4a56a908ef0a1df4df6fc33b8420e2e6c/luigi/worker.py#L146-L174).

**Proposed public contract:** add an opt-in `CheckpointTask` with `checkpoint_path()`, `checkpoint_version`, `initial_state()`, and `advance(state)` hooks. `advance` returns either `Transition(state=<JSON>, requires=<Luigi task structure>)` or `Finish(state=<JSON>)`. A versioned durable journal stores task identity, sequence, JSON state, transition status, and complete dependency descriptors. Do not attempt to serialize Python generators or arbitrary execution frames.

- Validate JSON state and the complete dependency descriptor structure before changing the durable cursor. Task identities use module/family/serialized parameters and retain nested list/tuple/dict structure for reconstructed dependency outputs. Reject unsupported state, cyclic structures, and self-dependencies clearly.
- Persist a transition and its newly discovered dependencies before exposing them to Luigi's worker. A restart reloads that committed transition and schedules or rechecks the same dependencies without calling the previous `advance` again. After dependencies are complete, resume with the committed state and reconstructed outputs through a documented argument or context accessor.
- A transition interrupted before its durable commit can be replayed. A committed transition cannot be replayed merely because a worker restarts. This is a state-commit guarantee, not exactly-once execution of arbitrary external side effects.
- Failed or still-incomplete children keep the parent at its waiting transition. A deleted child output is rechecked rather than trusted from a previous process's completion cache. Empty dependency structures advance normally. State is isolated by full task identity.
- `Finish` is committed only after ordinary task outputs are complete. `complete()` consults the journal and outputs together. If a previously finished output disappears, return false and raise a specific missing-final-output error on execution until explicit reset; do not silently rerun unknown effects.
- Add `checkpoint_status()` and explicit `reset_checkpoint(expected_sequence=...)`. Version or identity mismatch and a corrupt/truncated journal fail closed with diagnostic errors. Reset uses compare-and-swap and refuses while another process owns execution.
- A per-task interprocess lock serializes advancement, is released on process death, and is not held while child tasks execute. Sequence checks fence obsolete invocations after waiting. Preserve ordinary Task, DynamicRequirements, local-scheduler, and multiprocess behavior.

**Deterministic hidden verification:** implement a small three-stage importable fixture task that discovers dependencies from a JSON input and writes an append-only trace at each advance. Reconstruct it in a fresh interpreter after each committed transition; compare trace, state, child IDs, and final output. Use failing children, deleted child outputs, identical states with different significant task parameters, malformed state, journal truncation, version changes, reset conflicts, a subprocess terminated before journal replacement, and coordinated competing workers. A small model state machine can supply expected cursor progression independently of the reference journal implementation.

**Oracle feasibility:** a small explicit protocol plus atomic JSON journal and OS lock can build on Luigi's existing dynamic dependency mechanism. Integration needs careful distinction between committed/waiting/ready/finished states, reconstruction, worker completion caching, and parent-child error propagation. This does not depend on candidate 1 and should be implemented against clean upstream. Estimated difficulty is a hypothesis until the runnable task is measured.

**Public solution check:** current source search finds no checkpoint runner. GitHub issue search `repo:spotify/luigi checkpoint` returned three results; the relevant-looking #1523 concerns distributed scheduler state, not application transitions. `repo:spotify/luigi dynamic dependencies persist` returned zero. Web results mainly showed task-output checkpoints and application workflows. No matching full contract was found within this search scope. [Issue #1523](https://github.com/spotify/luigi/issues/1523) is adjacent context, not the proposed solution.

## 3. diskcache-resumable-reshard — historical write-blocking proposal

**Feature:** persisted shard topology and a bounded, restartable migration with an atomic topology switch.

**Why this is absent:** current `FanoutCache` creates numbered shard directories from the constructor argument and routes by `hash(key) % self._count`. The source has no persisted topology, reshard method, or migration journal. Reopening existing data with a different shard count does not migrate it. See [pinned initialization](https://github.com/grantjenks/python-diskcache/blob/ebfa37cd99d7ef716ec452ad8af4b4276a8e2233/diskcache/fanout.py#L19-L56) and [routing](https://github.com/grantjenks/python-diskcache/blob/ebfa37cd99d7ef716ec452ad8af4b4276a8e2233/diskcache/fanout.py#L257-L290).

**Source discrepancy to retain:** the hosted tutorial says FanoutCache transactions are unavailable, but the inspected current source implements `transact()` through an ExitStack of shard transactions. Do not base task novelty on transactions simply being absent. See [current transact implementation](https://github.com/grantjenks/python-diskcache/blob/ebfa37cd99d7ef716ec452ad8af4b4276a8e2233/diskcache/fanout.py#L69-L100).

**Proposed public contract:** add exported `ReshardableFanoutCache(directory, shards=None, ...)`, with `begin_reshard(new_shards)`, `step_reshard(max_items)`, `reshard_status()`, and `abort_reshard()`. Existing `FanoutCache` remains unchanged. New stores default to eight shards; existing managed stores load persisted topology when `shards=None` and reject an explicit mismatched count.

- Persist a versioned topology epoch and a durable migration record. Status includes source/destination counts, migration ID, phase, and durable copied-item count. Validate positive shard counts and step bounds. Beginning an identical active migration is idempotent; a different destination is rejected.
- `step_reshard` copies at most `max_items` source rows and checkpoints progress without loading the full cache into memory. Repeated calls and restart after a copied batch are idempotent. The source layout remains authoritative until complete validation and one atomic topology cutover.
- During an active migration, reads continue against the old generation. All logical mutations through this class raise `ReshardInProgress`, including mutating mapping methods, transactions, touch, expiration/culling, and `check(fix=True)`. Existing instances in other processes must observe this state before their next operation. Internal read statistics may change, but cannot affect copied logical values.
- Preserve key identity, values, absolute expiry timestamps, tags, binary/file-backed payloads, and disk serialization configuration. Migration cannot refresh TTL or evict entries due to destination size limits. Expired source rows may be copied with their original deadlines or skipped, but may never become live. Define the same policy for expired-key iteration and length in the final task specification.
- Cutover causes already-open instances to refresh their shard handles before their next operation. Abort before cutover discards only destination state and permits source writes again; abort after cutover is rejected. Interrupted cleanup is safe to resume. Readers holding already-open file descriptors remain valid on POSIX.
- Adoption of a legacy FanoutCache directory must be explicit and requires its known old shard count. Validate that all live rows route to their current shard before adopting. Preserve separately named `cache/`, `deque/`, and `index/` stores without resharding them. Reject nested migration/transaction usage and unsupported disk configuration changes.
- Cross-process locking protects begin, step, abort, and cutover. Process death releases operation locks; persisted migration state remains recoverable by another process. Do not promise online writes during migration or compatibility with old plain FanoutCache writers operating directly on the same adopted directory.

**Deterministic hidden verification:** migrate 2→5→1 shards with mixed typed keys, tagged records, expired records, and values larger than the disk spill threshold; compare an independent logical dump and absolute expiry times. Advance one-row batches, close, reopen, and resume; kill a process between destination-batch persistence and progress recording; verify duplicate replay does not alter values or count. Hold a second instance across begin, pause, abort, and cutover and test fencing/refresh. Verify bounded copying with a spy disk and many values; test named stores, explicit topology mismatch, adoption, corrupted metadata, interrupted cleanup, no data loss under tiny destination size limits, and existing FanoutCache regressions. A fake clock and multiprocessing barriers remove timing flakiness.

**Oracle feasibility:** immutable source/destination layouts, an atomic topology pointer, incremental row cursors, idempotent destination writes, and a topology lock form a practical reference design. Most complexity lies in preserving DiskCache's key/value storage modes, expiration behavior, and all mutator entry points. This is distinct from a verified snapshot/restore task: resharding changes routing topology in place with an active migration state machine, and does not define an export format or restore API.

**Public solution check:** GitHub issue search found zero results for `repo:grantjenks/python-diskcache reshard`; searches for shard changes and migration found unrelated issues and serialization-security PRs. Web searches returned base FanoutCache documentation and an alternative typed-diskcache API, with no matching restartable migration contract. Five expanded GitHub searches later failed with HTTP 403 rate limiting, so the scan is explicitly incomplete. The pinned current source remains the strongest evidence that this feature is not already implemented upstream.

**September 13 refresh:** an independent fetch inspected 27 open DiskCache PR titles/bodies and sampled active fork source, typed-diskcache, diskcache2, diskcache_rs and the published diskcache-weave distribution. The Rust alternative contains a database-only backup/migration helper, which is partial prior art rather than either final contract. The sampled sources did not supply a matching complete implementation; non-default branches and older/unpublished forks remain outside the scan. Exact scope, dates and primary links are in the [independent audit](independent-freshness-audit.md).

## Shared implementation and verifier requirements

- Freeze these base commits in each environment and build without network access during verification. Provide all project test dependencies and use only local files/processes.
- Keep tests and reference patches outside the agent-visible checkout. Tests should exercise public contracts and crash/reopen behavior, not merely repeat implementation logic.
- Run a baseline-failure check, full oracle pass, and representative mutant failures. Include semantic regressions of the underlying project. Binary reward may coexist with detailed per-group CTRF output for debugging.
- Every concurrency test uses explicit barriers/events/pipes and a short bounded timeout. Killing a cooperating child at a chosen phase is more deterministic than sleeping and hoping it reaches the relevant point.
- At the initial proposal stage these had research evidence and oracle designs only. Current construction and Harbor evidence are maintained in the [shortlist](shortlist.json); none of those solvability checks establishes model headroom or a >75-step horizon.
