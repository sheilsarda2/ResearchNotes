## 1. sqlite-utils-resumable-import — recommended first

**User problem.** Large NDJSON imports commit batches, but the CLI has no durable source position that allows a stopped job to continue safely. A user needs to resume after termination without duplicate rows, skipped rows, or a checkpoint ahead of committed data.

**Proposed public API.** Add `Table.insert_file_resumable(path, *, import_id, batch_size=100, pk=None, alter=False, upsert=False, progress=None)`. Add CLI command `sqlite-utils import-resumable DATABASE TABLE FILE --import-id ID [--batch-size N] [--pk COL ...] [--alter] [--upsert]`. The new command may share ordinary insertion helpers. Return a plain dictionary with `import_id`, `rows_committed`, `byte_offset`, `completed`; counts and offsets describe cumulative progress for this import. CLI emits that result as JSON. `progress(result)` is optional Python API notification after each committed batch, including the final batch.

**Bounded contract.** Accept a regular UTF-8 NDJSON file of JSON objects, optional leading UTF-8 BOM, CRLF/LF, blank lines, Unicode, and a final line without a newline. An import starts at byte zero, counts objects rather than physical lines, and stores byte offsets. Arrays/scalars and malformed JSON fail with a clear error. Do not support stdin, compressed files, CSV, arbitrary converters, list-mode records, or virtual tables in this task. Reject an existing caller transaction before mutation: durable per-batch checkpoints cannot be promised inside it.

Create `_sqlite_utils_imports`, keyed by `import_id`, with table name, full-file SHA-256, canonical insertion options, committed byte offset, cumulative object count, and completion flag. The path itself is not identity: identical bytes at a new path may resume. Table, file bytes, PK/upsert/alter configuration must match on reuse; batch size may change. Detect mismatch before changing the database, including when the import is already complete. A matching completed import is a no-op. Reserve the metadata table name as an invalid destination.

Read/hash the source without loading it into memory. Each insertion batch and its checkpoint update commit in the **same** transaction. Schema creation and `alter=True` column additions belong to that batch's transaction too. Earlier successful batches survive a later failure; every part of the failed batch rolls back. Exceptions from a post-commit progress callback propagate, leaving the reported committed checkpoint resumable. At EOF, completion and trailing whitespace position are recorded consistently, including empty input. Existing ordinary insert/upsert behavior remains compatible.

**Integration surface.** `db.py` insertion/type inference/transactions, `cli.py` command and exception handling, a focused import/checkpoint helper module or `utils.py`, exports if needed, Python+CLI documentation. Existing `insert_all()` adjusts effective batch sizes to SQLite's parameter limit, which must not desynchronize caller-visible checkpointing. The oracle can process one logical batch inside `db.atomic()` and let `insert_all()` create nested savepoints; ledger advancement occurs only after all internal sub-batches succeed.

**Deterministic hidden verification.** Invoke both API and CLI in fresh subprocesses and reconnect to inspect persisted rows and ledger. Use an insert trigger to fail a late batch, remove it, resume the unchanged source, and compare against a clean one-shot reference. Use a trigger on the checkpoint table to fail checkpoint advancement after row writes; no rows from that batch may remain. Terminate a child with `os._exit()` in the post-commit callback and resume in another process. Test duplicates with upsert, composite keys, dynamic columns appearing in a failed batch, byte offsets with multibyte text/CRLF/BOM, empty file, malformed lines, option/source mismatch, callback exception, complete rerun, and nested-transaction refusal. These tests need no timing-sensitive signal delivery.

**Plausible oracle scope.** Roughly 250–450 implementation lines plus CLI/docs and independently authored tests. This is an estimate, not a size requirement. Build a streaming reader, validate identity, look up progress, seek, process batches, and update the ledger inside each transaction. Run the existing insert/upsert/atomic/CLI tests plus the contract verifier. No public implementation of this particular feature was found in source, inspected open issues, or targeted web searches. Related byte-counting PRs #810/#812/#856 concern progress display, not recovery state.

**Main risks.** A wrapper that merely adds `resume=True` to `insert_all()` is insufficient; batch boundaries, metadata failure, schema rollback, and complete reruns supply the real difficulty. Avoid overloading the contract with concurrency leases or network-source support. Fingerprinting the full file makes startup linear in source size but keeps identity checking simple and deterministic.

## 2. sqlite-utils-merge-remapped-graph — viable, with disclosed overlap

**User problem.** Two offline databases contain independent integer ID spaces. Concatenating their related tables either conflicts or attaches imported children to unrelated destination parents. Merge the whole relational graph while allocating fresh destination IDs, preserving existing destination rows and source relationships.

**Proposed API.** `Database.merge_preserving_keys(sources, *, tables)` where each source is `(source_id, path)`; CLI `merge-preserving-keys DEST --source ID PATH ... --table NAME ...`. Return deterministic inserted counts and old-to-new key maps by source/table. Initially require existing destination tables with matching columns and declared FK structure; every selected table has one `INTEGER PRIMARY KEY`. Support multiple ordinary single-column FKs, null references, self-references and cycles. Reject virtual tables, selected source-table triggers, unsupported PK/FK layouts, and source FKs leaving the selected table set before mutation.

For each source/table, reserve all IDs in ascending old-ID order, assigning from `max(0, destination max ID)+1`; plan every table before inserting any row. Rewrite FK values using those maps. Source/table order is canonical and independent of caller table order. Preserve ordinary values including blobs. Destination triggers execute normally and their effects belong to the merge transaction. Violations of non-PK uniqueness or triggers fail the entire call without leaving any new source imported. Preserve caller transactions using savepoints, and restore all changed pragmas. Use deferred constraints plus a final FK check, rather than silently disabling validation.

Persist provenance and maps in reserved metadata tables atomically with imported rows. Reusing a source ID with the same canonical selected-schema/row fingerprint is a no-op; changed source content under the same ID is an error. The fingerprint must represent the SQLite snapshot, not just hash the main file while ignoring WAL. No source database may be modified.

**Verifier.** Three overlapping ID spaces, reversed input/table order, self-reference, cycles, null FKs, invalid source closure, destination uniqueness collision after earlier tables have inserted, failure during provenance recording, caller transaction rollback, clean reconnection, idempotent rerun, source drift, unchanged source logical dumps, and metadata rollback. Test completed destination joins, not just row counts.

**Freshness/overlap.** [Issue #491](https://github.com/simonw/sqlite-utils/issues/491) and open [PR #724](https://github.com/simonw/sqlite-utils/pull/724) already propose generic database merging. Inspected PR code loops over `insert_all()` with preserve/replace/ignore PK behavior; it does not implement FK remapping, graph-wide allocation, provenance, or graph-wide transactional semantics. Cite it as prior art. The new task must retain those substantive differences.

**Oracle scope/risk.** About 350–650 implementation lines, with introspection, graph planning, snapshot digesting, insertion, metadata and CLI layers. The integer-PK restriction keeps a reference solution feasible. General composite-key remapping and automatic schema reconciliation would expand scope too far for this candidate batch.

## 3. sqlite-utils-atomic-schema-plan — reserve candidate

**User problem.** A schema change can leave the rows intact but silently remove audit triggers or strand dependent views. Users need a coordinated schema plan whose dependent objects work after both successful execution and failure recovery.

**Proposed API.** `Database.transform_schema(plan, *, dry_run=False)` plus `sqlite-utils transform-schema DB PLAN.json [--dry-run]`. Plan is a mapping of existing table names to allowed transformations: column renames, types, order, NOT NULL/default changes and drops. Use existing transform meanings for column references. Plan execution is all-or-nothing across tables. Dry-run returns SQL or a stable structured description and must not mutate the database. The executor must reject changes that cannot preserve dependent semantics before committing, naming the dependent object.

Preserve and update ordinary indexes including partial/expression indexes, view chains, arbitrary user triggers including `UPDATE OF`, incoming/outgoing/self FKs and FK actions. Preserve string literals and comments that happen to contain old identifier text. Keep unaffected view result-column aliases stable. Recreate transformed-table triggers after the row-copy stage so data migration does not fire business audit actions. Preserve rowids, AUTOINCREMENT high-water marks, existing CHECK/UNIQUE constraints and original pragma settings. A failed later table rebuild rolls back earlier renames, dependency rewrites, rows, trigger changes and temporary objects. Reject virtual tables/generated columns and intrinsically invalid drops instead of silently dropping dependencies. Top-level execution only is acceptable if documented because FK pragmas cannot be toggled inside a caller transaction.

**Do not require handwritten SQL rewriting.** SQLite native `ALTER TABLE ... RENAME COLUMN` already rewrites dependent expressions correctly. A legitimate oracle should use SQLite's own parser for rename stages, capture resulting dependent SQL, then perform necessary table rebuilds and recreate objects inside a coordinated transaction. A task consisting of renames alone would be too easy. The proposed composition with type changes, ordered multi-table execution, dry-run, dependency failures, pragma restoration and transactional rollback creates the additional work. If that composition is still shallow in oracle implementation, drop this candidate rather than force artificial complexity.

**Verifier.** A two-table rename plus strict/type conversion and reordering; view-on-view queries; triggers on transformed and untouched tables; expression/partial index enforcement; FKs with CASCADE actions that must not fire during rebuild; source text literal preservation; gapped rowids; deleted AUTOINCREMENT maximum; an invalid later conversion that restores the complete logical schema/data; dry-run on a read-only connection; invalid dependency drop and no leftover temporary tables.

**Freshness/overlap.** [Issue #849](https://github.com/simonw/sqlite-utils/issues/849) and September 6 [PR #854](https://github.com/simonw/sqlite-utils/pull/854) document current trigger loss and unchanged view definitions. [PR #703](https://github.com/simonw/sqlite-utils/pull/703) already supplies an incoming-FK rename approach; [PR #499](https://github.com/simonw/sqlite-utils/pull/499) attempts FTS trigger recreation. None is the proposed coordinated plan, but all are relevant prior solutions and must be disclosed. Native SQLite [ALTER TABLE documentation](https://www.sqlite.org/lang_altertable.html) is the reference for dependency rewrite behavior.

**Current native support and pinned runtime.** [SQLite 3.53.0](https://www.sqlite.org/releaselog/3_53_0.html), released April 9, 2026, added ALTER support for NOT NULL and CHECK constraints. The final schema-plan container records SQLite 3.40.1, so its nullability handling includes compatibility with an older runtime. Do not claim that current SQLite cannot alter nullability or that native dependency-aware renames are new. The remaining contract composes transformations, explicit conversions, dependency/identity preservation, atomic multi-table outcomes and isolated data-validating previews. The [independent audit](independent-freshness-audit.md) also confirms PR854 and September 13 PR861 are documentation-only. Preserve the frozen runtime for this pack; a future runtime upgrade needs a new verified version.

**Oracle scope/risk.** About 350–700 implementation lines if native renames and existing rebuild code compose well. Highest risk of the three: broad dependencies can become an accidental SQL parser project. Keep it a reserve candidate until a bounded oracle demonstrates the contract is feasible. Do not call it novel solely because an old open issue has not merged.
