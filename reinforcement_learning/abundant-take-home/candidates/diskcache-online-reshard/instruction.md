## Durable lifecycle API

All lifecycle methods return a fresh dictionary with these keys: `epoch` (starts at zero), `shards` (active count), `generation` (opaque stable active-generation string), `migration_id` (opaque string or None), `phase` (`idle`, `copy`, `reconcile`, or `paused`), `target_shards` (integer or None), `copied` (nonnegative durable migration work count, zero when idle), and `pending` (nonnegative remaining mutation-reconciliation work, zero when idle). Callers may mutate returned dictionaries without affecting cache state.

* `reshard_status()` reads durable state; every client refreshes topology before each top-level operation.
* `begin_reshard(shards, expected_epoch=None)` starts a migration. Optional nonnegative integer epoch is compare-and-swap fencing: stale epoch raises conflict. Repeating an active request for the same count returns the same migration ID and progress; another target conflicts. Requesting the current count while idle is an idempotent no-op. Begin prepares tracking/storage but does not copy all entries.
* `step_reshard(migration_id, max_items=100)` performs at most `max_items` source-entry copies or mutation reconciliations and adds `processed` to the result. Validate a positive integer budget. Empty-shard traversal and cutover bookkeeping do not count as entries; this is an entry-work bound, not a wall-clock or byte bound. Copy large file payloads by streaming rather than reading/deserializing an entire payload. Persist progress so another instance/process can resume. When all baseline work and intervening mutations have been reconciled, atomically publish the new active topology, increment epoch exactly once, and return idle. A final zero-work call may be necessary. No full synchronous copy at begin, reopen, pause, or resume.
* `pause_reshard(id)` and `resume_reshard(id)` are idempotent. Paused migrations survive reopen and permit normal reads/writes; a step while paused raises `ReshardPausedError`.
* `abort_reshard(id)` discards unpublished destination work, leaves the old topology/epoch active, and preserves every committed source mutation. It is recoverable if interrupted during cleanup. Starting again uses a fresh migration ID.
* `collect()` reclaims retired generations after successful cutover and returns the number collected. It is explicit and may do unbounded cleanup. Repeated calls return zero. It must not delete active, in-progress, or named-store data. An already open read stream remains usable after cutover/collection on the supported filesystem.

Every step/pause/resume/abort requires the current migration ID. Missing, replaced, aborted, or completed IDs raise `ReshardConflictError`. Lifecycle mutations inside a native `transact` block raise `ReshardBusyError` before changing topology.

## Consistency and recovery

Normal managed reads and writes continue against the authoritative source between migration steps, including while paused. Each operation observes one active topology. Changes made after a row was copied must reach the final destination: overwrites, deletes, delete/reinsert, `add`, increments, touches, expired-row removal, tag eviction, clearing, culling, and successful transaction batches. A rolled-back transaction must not leak either values or migration bookkeeping. Preserve original absolute expiration deadlines, tags, inline/file-backed bytes/text/pickled values and JSONDisk encoding. Natural expiry must never resurrect an entry at cutover. Migration itself must not invoke ordinary capacity eviction on copied entries. At quiescence, repeated bounded steps must finish, and the final logical cache must match the source immediately before cutover. Continuous writes may defer completion.

Coordinate managed clients across instances, threads, and processes using a host-local lease. Nonblocking contention may raise `ReshardBusyError` before performing the contending operation; clients can retry. A native transaction owns the root lease until its outermost exit. Do not silently drop operations on lease contention. Process death releases ownership; old instances refresh rather than continuing to use a retired topology. Native FanoutCache already implements `transact`: retain its ordinary successful-exit/exception rollback behavior, but do not claim stronger crash-atomic transactions spanning several independent SQLite databases or exactly-once external side effects.

Durable topology and progress must survive abrupt process termination at arbitrary points in begin, copying, reconciliation, cutover, and abort. Before cutover, the source remains authoritative; recovery must replay incomplete work without losing later updates or duplicating entries. After a published cutover, reopen must use the complete destination and never roll back the epoch. Handle partial destination files safely. This task requires local process-crash recovery, not storage-device failure, power-loss guarantees, network filesystems, or malicious concurrent modification of cache internals.

Use a single root `RESHARD.json` as the authoritative topology commit record. Its public envelope is `{"schema":1,"data":<object>,"sha256":<hex>}`; the digest is SHA256 of `json.dumps(data, sort_keys=True, separators=(",", ":"), allow_nan=False).encode()`. The data object contains `epoch`, `active` with `generation` and `shards`, and `migration` (None or an object including `id`, `phase`, and `target` with generation/shards); other bookkeeping is implementation-defined. Publish atomically with `os.replace`; never expose a truncated/partially written record. Unknown schema, checksum mismatch, malformed metadata, or a missing/unreadable payload encountered during copying raises `ReshardIntegrityError`, without publishing incomplete data. A root with invalid metadata must not be treated as a new empty cache. Internal generation naming is free. You may use recoverable intermediate preparation/abort states in this record; they must settle before normal operations and not escape through the status API.
