# Add a durable terminal-failure archive and atomic redrive to Huey

This repository is current Huey at commit `dbd1aef45adf57d2169e80bdc9f18ea1cd704759`, inspected September 13, 2026. A task error result is optional, consumable, and does not preserve the invocation needed for replay. Operators need a durable inventory of exhausted failures and a deliberate, atomic way to submit each failure once as new work.

Implement this as an opt-in extension of the existing package and document its API. Preserve ordinary Huey behavior and default storage schemas when the feature is disabled. Upstream tests are available. Do not change the verifier.

## Public API and persistent records

Accept `failure_archive=True` on `SqliteHuey`; default is `False`. Require an on-disk SQLite backend when enabled, with clear rejection of incompatible storage or `:memory:`. Initialize archive tables together with the configured SQLite storage schema. Respect `create_tables=False`: construction creates no tables; explicit `huey.storage.initialize_schema()` initializes them. For immediate mode with memory debug storage, initialize the configured file through a normal SQLite instance first when automatic creation is disabled. Existing queue, schedule, result and unrelated application data remain usable. Queue names isolate every archive operation.

Add these methods on `SqliteHuey`; when archiving is disabled they raise `ConfigurationError`:

- `failures(limit=100, after=None)`: non-destructive ascending pagination. `limit` is a positive integer excluding booleans; `after` is `None` or a nonnegative integer cursor, and is exclusive. New records have strictly increasing integer cursors; deleting a record does not recycle its cursor.
- `failure(failure_id)`: return a record or `None` when absent for this queue.
- `redrive(failure_id, retries=0, delay=None, priority=None)`: atomically create one replacement for this failure and return its durable receipt. A missing failure raises `KeyError`. `retries` is a nonnegative integer excluding booleans. `delay` is `None` or a finite, nonnegative number of seconds excluding booleans. A specified `priority` is a finite number excluding booleans. Reject invalid options without modifying the archive or queue.
- `delete_failure(failure_id)`: delete just that record, returning a boolean. It does not erase other failures, ordinary results, already queued replacements or lineage links. Deleting a parent must not prevent a later child failure from retaining that parent's ID.

Export `FailureRecord` and `RedriveReceipt` from `huey.contrib.deadletter`. A `FailureRecord` exposes `failure_id` (stable string), `cursor`, `task_id`, `name` (registered task name), `error`, `traceback`, `failed_at` (UTC Unix seconds), `data` (serialized original invocation, decodable with `huey.deserialize_task()`), `parent_failure_id` (string or `None`), `redriven` (boolean snapshot), and `replacement_id` (new root task ID or `None`). These are durable snapshots and reads must not mutate stored data. Listing failure metadata does not require task functions to be registered; replay/decoding does.

A `RedriveReceipt` exposes `failure_id`, `task_id` (new root ID), `task_ids` (all newly assigned IDs in deterministic root/success/error traversal order), and `result`. With results enabled, the result handle has ordinary `Result` or success-pipeline `ResultGroup` reading behavior; with results disabled it is `None`. Repeated redrive calls, including after messages/results have been consumed and across processes, return the same replacement identity and do not enqueue again. For a valid later call, the first committed call's options win; do not rewrite its message or receipt. Result handles need not preserve arguments for rescheduling.

## Capture at the correct execution boundary

Archive only executed, terminal errors with no retry remaining after Huey's retry decision. Ordinary task exceptions, exhausted `TaskTimeout`, `TaskLockedException` and non-retrying `RateLimitExceeded` are failures. Automatic intermediate retries, retry exhaustion that ultimately succeeds, and `RetryTask` requeues are not terminal archive records. `CancelExecution` is a deliberate control-flow outcome and is never archived, whether or not it retries. Revoked/expired tasks, pre-execute cancellation, and interrupted execution (`KeyboardInterrupt`/process disappearance) are not archived. Do not infer this classification solely from emitted signals or result-store contents.

Periodic invocations are excluded from this archive. Capture the invocation at the beginning of each eligible execution attempt, before pre-execute hooks or task code can mutate its args/kwargs, options or callback links. It is the terminal attempt's initial invocation, not necessarily the first-ever attempt. Its retries/delay/backoff reflect that attempt. Snapshot and archive operations must not modify the task that Huey executes. Preserve the configured serializer/compression, exception traceback and original task identity. Snapshot/archival storage failures should surface rather than silently claiming the failure was durably recorded.

Recording is independent of `results`, `store_intermediate_errors`, ordinary result reads and `storage.flush_results()`. Existing success/error callbacks, retry/backoff, timeout, revocation, hooks, chord outcomes and consumer execution retain their behavior. Archive capture must occur before user post-execute hooks and error callbacks can change the invocation or throw away its context. This task does not promise an archive entry for a process killed before recording commits or make the whole executor transactionally atomic.

## Redrive as a new detached invocation

Reconstruct from the stored pre-mutation invocation. Give the root and every reachable success/error callback task a fresh unique ID; do not overwrite old result identities. Preserve original arguments, kwargs, registered classes, retry delay/backoff, timeout and callback options. Root `retries` comes from the redrive call; callback retry budgets retain their stored values. Root priority is overridden only when provided.

Clear old ETA on every replayed task. Root delay `None`/zero means immediately queued; a positive delay gives the root a fresh future ETA, with ordinary consumers/scheduler handling it. Clear stored `expires_resolved` throughout the replay. Preserve relative expiry values and resolve the root's relative expiry from redrive time; downstream relative expiry starts on its normal enqueue. Clear absolute datetime expiration deadlines throughout the replay so an old deadline cannot silently suppress deliberately redriven work.

Detach **all** old chord configurations on the root and its success/error callback chains. Replaying a failed chord member must not increment old chord counters or enqueue the old chord callback again, including when a pipeline tail or an error callback carried the binding. Do not recursively replay the callback graph reachable only through an old chord configuration. Ordinary explicitly attached success/error pipelines still execute with their new IDs.

A failed replacement or its fresh callback produces a separate archive record linked by `parent_failure_id` to the failure that created that replay graph. Automatic retries of a replacement retain that lineage. A later redrive of the new failure creates another generation; older failure metadata and ordinary error results remain unchanged. Persist lineage across processes without breaking compatibility with already serialized Huey messages.

Insert the replacement queue message, reserve the one-time receipt, and persist all new lineage links in one transaction in the same SQLite database. Competing redrivers must return one identity and queue one root. An insertion/serialization failure or process death during this transaction leaves the original failure unclaimed and no partial replacement/lineage. Retrying can then create a complete replacement. The first successful commit permanently reserves that failure's redrive until the failure is deliberately deleted.

Redrive always queues work and never executes task bodies inline, including immediate mode. Immediate mode's default memory debug storage may still serve ordinary calls, but archive records, redrive messages and receipt reads must use the configured SQLite broker. A normal SQLite consumer executes replacements. Reading APIs must survive constructing a fresh Huey instance. Archiving-disabled instances continue behaving as upstream; no Redis archive, global dead-letter service, malformed-message quarantine, worker lease protocol or exactly-once external task effects are required.

Evaluation uses a fresh offline container with the pinned dependencies. Only `/workspace/repo/huey/` is transferred as the submitted implementation. Keep runtime feature code inside that package; upstream tests and documentation may also be edited for development but do not replace the independent verifier.
